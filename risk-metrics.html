Rule Hit Rate｜规则命中率

1）是什么：在真正进入该规则评估的申请中，有多少触发规则；它看的是信号/流量与规则阈值的交集。

2）为什么重要：模型与策略的领先/同步过程指标，可快速发现攻击、流量、Vendor字段或规则版本变化，但Hit不等于最终Reject或真实Fraud。

3）公式：Rule Hit Rate = 触发规则的唯一Application/用户 ÷ 实际被该规则评估的唯一Application/用户必须固定规则版本、时间窗、订单/用户口径和重复尝试去重。

4）高低：升高可能攻击上升、渠道变差、数据漂移或阈值变严；下降可能流量改善也可能规则失效。不存在越高越好。

5）墨西哥案例：首贷V7新增设备/手机号/CLABE规则，30,000申请，Hit 22%→35%、Unique Reject8%→14%、Review12%→24%、Override2%→9%、Confirmed Fraud3.8%→4.1%、Approval34%→28%、投诉0.7%→1.5%。拆解发现三条规则Overlap>45%，Channel C新设备贡献多数新增Hit；可确认重复度上升，但不能仅凭Hit说攻击翻倍。高Overlap规则降为Step-up，强图谱硬拒保留，观察两个成熟Fraud/FPD7 Cohort。

6）诊断：规则版本/分母 → 字段Missing/Vendor → Channel/Device/Score → Overlap/Unique Reject → Fraud Outcome/FPR。

7）动作：数据异常修Vendor；渠道异常降量；高Hit低增量降为Step-up/Review；高Hit高Fraud Capture且FPR低可保留硬拒。

8）误区：Hit=Reject；重复申请重复计数；分母用全量但规则只覆盖部分；Hit增长直接当欺诈增长。

9）拆分：Rule/Version、Channel、Campaign、Device、Score、Limit、Region、新老客、Vendor、Strategy。

10）预警：同版本历史基线；Hit超历史稳定区间只是黄灯候选，必须叠加Missing、Overlap和Outcome；阈值仅为内部设计。

11）关系：Signal/Data → Rule Hit → Overlap → Unique Reject/Review → Approval → Fraud Capture/FPR → Net Loss。

12）练习

Hit从10%升20%，但Missing从1%升18%、Fraud Capture不变，先做什么？答案：先查数据/Vendor和分母。

Unique Reject Rate｜唯一拒绝率 / 增量拒绝率

1）是什么：去除规则重叠后，某条规则/规则组真正新增造成的Final Decline比例。

2）为什么重要：同步策略影响指标，防止多条重叠规则分别把同一批用户计为“贡献”。

3）公式：Unique Reject Rate = 因目标规则/规则组形成唯一Final Decline的Eligible Applications ÷ Eligible Applications可进一步估Incremental Reject：如果去掉该规则，本来会通过/Review但现在被其拒的比例。

4）高低：高说明规则对Approval影响大，但需与Fraud Capture、FPR、Override、投诉和Margin联动判断。

5）墨西哥案例：三条设备/手机号/CLABE规则Hit合计很高，但去重Unique Reject仅14%；Rule A Hit18%、独立Unique Reject2.6%、Override38%、Fraud Capture增量0.15pp，Approval因组合下降4pp。多数A命中同时被B/C覆盖，A降为Step-up做Challenger；若Approval恢复、Fraud Loss无显著恶化、投诉下降，才证明优化有效。

6）诊断：Final Action → Overlap Matrix → First-hit/Decision Priority → Override/FPR → Fraud Loss/FPD/Margin。

7）动作：高Overlap低Unique Reject合并/降级；高Unique Reject低价值收窄；高Unique Reject高捕获保留；通过Challenger验证删除/降级。

8）误区：所有Hit都算拒绝；忽略Overlap；把Final Reject归因给最后命中规则；忽略优先级和Hard Rule。

9）拆分：Rule Family、Channel、Score、Device、Limit、Fraud Type、Strategy Version。

10）预警：Unique Reject突然上升且Approval下降应报警；若Fraud Capture未同步提升为黄灯，投诉/Margin也恶化可红灯。

11）关系：Rule Hit → Overlap/Dedup → Unique Reject → Approval → Take-up → Fraud/FPD → Margin。

12）练习

三条规则Hit 10%/8%/7%，去重最终只拒绝11%。能说总拒绝25%吗？答案：不能。

Manual Review Rate｜人工审核率

1）是什么：Eligible申请中进入人工Case的比例；看自动策略把多少工作量交给人。

2）为什么重要：贷前/欺诈同步运营指标，决定产能、TAT、成本和客户体验，也反映规则/模型的不确定性。

3）公式：Manual Review Rate = 有效人工Case的唯一申请 ÷ Eligible Applications必须明确重复复审、补件、二审的去重方式，并另报Case/Reviewer、P50/P90 TAT、Cost/Case。

4）高低：过低可能漏风险，过高可能策略过宽或自动化不足；必须用增量Fraud Capture和经济价值评估。

5）墨西哥案例：V7后Review12%→24%、P90 TAT18→52分钟、Approval34%→28%、Review后约31%被改为Approve、Confirmed Fraud增量仅0.3pp、Cost/Application7→13 MXN。Review集中Channel C的新设备低风险Score；将低风险段回自动Allow/Step-up，高风险图谱保留Review，观察Fraud Loss和投诉。

6）诊断：Case定义/重复 → Rule/Reason → TAT/Capacity → Outcome/Override → Fraud Capture/Approval/Complaint。

7）动作：Review高低价值缩规则；Backlog高调优先级/班次；高余额高风险提高人工优先级；低风险重复Case自动化。

8）误区：Review越多越安全；重复Case多计；不看TAT；审核通过全部算误报。

9）拆分：Rule/Reason、Channel、Score、Limit、Device、Reviewer/Vendor、Time Slot、Strategy。

10）预警：Review Rate、P90 TAT、Backlog、Cost/Case、Override、Fraud Capture联合；阈值来自自身稳定期。

11）关系：Rule/Model Uncertainty → Manual Review → Outcome/Override → Approval → Fraud Loss / Cost / CX。

12）练习

Review翻倍但Fraud Capture仅+0.2pp、TAT翻倍，能说策略更安全吗？答案：不能。

Override Rate｜人工改判率

1）是什么：系统初始Decision被授权人工/上层策略改成不同最终动作的比例。

2）为什么重要：模型与策略治理核心指标，用于发现规则边界问题、运营绕过、权限滥用和决策不一致。

3）公式：Override Rate = 被合法改写初始Decision的唯一Decision ÷ 允许进入Override流程的唯一Decision必须按Decline→Approve、Approve→Decline、Limit Override、KYC Override区分，并保存Owner、Reason、Evidence。

4）高低：高可能规则需要修正，也可能人工权限滥用；低也不一定好，可能审核员不敢纠错。看方向、Reason和后续Outcome。

5）墨西哥案例：V7后Override2%→9%，其中Decline→Approve占78%；这些账户FPD7约17% vs 自动Approve组14%，运营Team A Override达16%，大量Reason是自由文本“重点用户”。确认权限/Reason治理不足，但不能只凭FPD更高就说全部Override错误。动作：Hard Fraud Rule禁Override，边缘信用设置额度上限Override，高风险Override双人审批，营销不得覆盖安全规则；观察Override Cohort的Fraud/FPD/Margin。

6）诊断：Override方向/权限 → Reason/Evidence → Team/Rule/Segment → Fraud/FPD → Margin/Complaint/Audit。

7）动作：硬风险禁止Override；边缘信用限额Override；异常团队收权限；持续高Override规则进入再设计/Challenger。

8）误区：越低越好；人工Approve就说明规则错；自由文本Reason足够；运营/客服可无审计改判。

9）拆分：Direction、Reason、Reviewer/Team、Rule、Score、Limit、Channel、新老客、Strategy Version。

10）预警：按Team/Reason稳定区间；Override激增、Hard Rule被覆盖、后续Fraud/FPD恶化任一出现均升级，数值阈值只用内部基线。

11）关系：Initial Decision → Manual Review → Override → Final Decision → Approval/Limit → Fraud/FPD → Margin/Audit。

12）练习

某团队Override15%、其他团队3%，且Reason大量为空，先做什么？答案：先收紧异常权限并审计样本/Reason。
