今日联合判断框架

Query Success → Bureau Hit → Thin-file → Inquiry Velocity → Approval/Limit → FPD/Vintage → EL/Margin

先区分技术失败与真实信用信息稀薄，再谈风险。Query Success下降但成熟Outcome稳定，优先技术治理；Hit下降、Thin-file和Inquiry同时上升且FPD/EL恶化，才更像客群/信用风险变化。

Bureau Query Success Rate｜征信查询技术成功率

1）是什么：发起查询中成功得到可判定技术响应的比例。

2）重要性：贷前同步/领先技术指标，解决“没结果是系统失败还是客户没档案”。

3）公式：技术成功唯一查询 ÷ Eligible且已发起的唯一查询固定Vendor、接口版本、授权、超时窗口；Retry按Application去重。

4）高低：通常越高越好；下降常见于Vendor、授权、网络、字段格式、版本问题，高成功率不代表征信质量高。

5）七步案例：月60k申请，Query Success 98%→94%、Hit 82%→69%、FPD7 14.5%→18.2%；部分Android新版超时明显，重试成功客户并未显著更坏；技术问题与客群变化并存；决策为Retry/Fallback与信用决策分离；观察成功率、成本、Approval与成熟FPD。

6）诊断：Consent → Error Code → OS/Network → 字段 → Retry Outcome。

7）动作：技术失败先Retry/Fallback；持续故障切备用Vendor；授权缺失重新授权；大面积字段错误回滚。

8）误区：Technical Fail算No-hit；重复Retry重复计数；无档案响应算技术失败。

9）拆分：Vendor、App/OS、Device、Network、Region、Channel、Error Code、Version。

10）预警：用小时/日自身历史和最低查询量；低于历史稳定区间且Timeout升高可设内部黄灯。

11）关系：Consent/Data → Query Success → Bureau Hit → Score/Thin-file → Approval/Limit → FPD。

12）练习

10,000笔查询、9,500技术成功，Query Success=95%。

Bureau Hit Rate｜征信命中率

1）是什么：技术查询成功样本中找到有效信用档案的比例。

2）重要性：决定Score、Inquiry、多头、历史还款等信息是否可用。

3）公式：有效信用档案唯一申请 ÷ 技术查询成功唯一申请Technical Fail必须排除。

4）高低：高通常意味着正式信用体系覆盖更充分；下降也可能来自年轻客、渠道变化、身份匹配或Vendor覆盖，不等于风险必然变坏。

5）七步案例：Hit 82%→69%、Thin-file 18%→31%、Approval 30%→34%、FPD7 14.5%→18.2%；Channel C命中低但稳定工资低Inquiry组尚可；高Limit组显著恶化；决策是按File Depth/Inquiry分层而非统一拒绝。

6）诊断：Query Success → 身份匹配 → Channel/年龄/就业 → File Depth → FPD/EL。

7）动作：Hit下降但Outcome稳定不自动收紧；No-hit进入Thin-file策略；身份异常修KYC；特定渠道Hit降且风险恶化则降量/降额。

8）误区：用全部申请作分母；No-hit=好客；No-hit=坏客；跨Vendor直接比。

9）拆分：Channel、Campaign、Age、Employment、Region、Vendor、Document、新老客。

10）预警：Hit下降只有与File Depth/Inquiry/FPD/EL同步恶化时才升级风险告警。

11）关系：Query Success → Hit → Thin-file/File Depth → Score/Inquiry → Approval → FPD/EL。

12）练习

9,500技术成功、7,125有档案，Hit=75%。

Thin-file Rate｜薄征信占比

1）是什么：有征信档案但信用历史深度不足的客户占比。

2）重要性：决定模型特征可用性、准入不确定性与替代数据需求。

3）公式：符合内部Thin-file定义的Bureau-hit唯一申请 ÷ Bureau-hit唯一申请定义需版本化，不存在行业唯一公式。

4）高低：上升不一定坏，可能代表触达新到信用户；与高Inquiry、高Limit、FPD恶化同现时更值得警惕。

5）七步案例：Thin-file 18%→31%；C渠道Thin-file×Limit≥2,000 FPD7约25%，稳定工资低Inquiry约13%；因此采取分层Challenger与额度Guardrail，而非统一拒绝。

6）诊断：规则版本 → File Depth → Inquiry/Income/Device → Limit/Term → FPD/Vintage。

7）动作：低Inquiry稳定客用小额度验证；高Inquiry/高波动收入降额；替代数据需验证稳定性、偏差和隐私。

8）误区：No-hit=Thin-file；定义混用；替代数据覆盖多=安全；只看件数风险。

9）拆分：Channel、Age、Employment、Income Type、Inquiry、Limit、Term、Device、Region。

10）预警：Thin-file上升且High Inquiry、Amount FPD、EL同步恶化可设内部黄灯。

11）关系：Bureau Hit → Thin-file → Alternative Data → Limit → FPD/Vintage → EL/LTV。

12）练习

7,000个Hit客户中2,100个Thin-file，Thin-file Rate=30%。

Inquiry Velocity｜征信查询速度

1）是什么：决策前固定窗口内的信贷查询次数/速度，反映近期是否集中申请借款。

2）重要性：贷前领先指标，用于识别多头、资金压力和申请攻击。

3）公式：Inquiry_7d / Inquiry_30d = 决策时点前7/30天符合内部信贷申请定义的唯一查询数按Inquiry Type/Institution必要去重，只能用决策时点之前的数据。

4）高低：短期快速上升通常更值得警惕，但不同查询类型、比价、例行查询不能混为一谈。

5）七步案例：30日Inquiry中位数1.4→2.6；High Inquiry×Thin-file×High Limit FPD7约25%，低Inquiry稳定工资组约13%；相关性明显但Channel/Limit同时变化，因此以分层Challenger验证。

6）诊断：Inquiry Type/去重 → 7d/30d → File Depth → Channel/Score/Limit → FPD/EL。

7）动作：短期爆发可降额/延迟/Step-up；稳定客户合理查询不机械拒绝；异常重复先查身份盗用/Vendor。

8）误区：全部查询当借贷申请；决策后数据穿越；只看30天总量不看7天速度；因果倒置。

9）拆分：Window、Inquiry Type、Institution Type、Channel、Score、Thin-file、Limit、Region、Device。

10）预警：用内部历史分位数；High Inquiry占比持续上升且FPD/EL恶化才升级。具体次数不是行业标准。

11）关系：Income Stress/Acquisition → Inquiry Velocity → Multi-Borrowing → Limit/EAD → FPD/Roll → Bad/EL。

12）练习

两人30天均6次查询，但A过去7天有5次、B分散整月，A的短期Velocity更高。
