第三部分【海外风控知识学习】

今日主题：Payment Failure Taxonomy & Retry Strategy｜支付失败分类与重试治理

概念：还款失败不应直接等于“客户没钱/信用变差”。支付失败至少应拆成 Hard Failure、Soft Failure、Technical Failure、Account/Identity Mismatch 和 Customer Cash-flow Failure，再决定是否重试、换通道、Step-up或进入催收。

First Attempt Success → Failure Taxonomy → Retry → Final Payment Success@N → Cure / Roll / FPD

为什么重要：如果把技术超时和余额不足混在一起，会把支付系统问题误判成信用风险；如果对Hard Fail持续自动重试，又会制造成本、投诉和重复扣款风险。

墨西哥现金贷七步案例（模拟）

背景：30天现金贷切换新Payment Router，并启用自动Retry；Channel C同时上线银行卡变更功能。
数据：到期账户12,000、Due Amount MXN18m；First Attempt Success 72%→63%；7日Payment Success 82%→86%；Retry Recovery约36%→62%；Bank/Account Mismatch 2.1%→4.6%；FPD7 17.6%→15.8%。
现象：首扣成功显著下降，但最终7日回收反而改善；说明“首扣失败”和“真实信用坏账”发生分离。
拆解：Temporary Bank Error / Insufficient Balance的Retry效果好；Channel C×Recent Bank Change的Account Mismatch明显更高；Hard Invalid Account重复Retry基本无增益。
根因：可以确认新Router、Bank Change和失败结构变化与指标同时变化；但在完成通道对照与错误码映射前，不能把全部改善归因于Retry。
决策：Soft/Technical Fail做指数退避或时段优化Retry；Hard Invalid停止重试并引导换账户；Bank Change + Device Change做Step-up和账户复核；支付技术失败不直接计入信用拒绝/欺诈。
结果：观察7—14天 First Attempt、Retry Recovery、Final PSR、FPD7、Roll30、Payment Cost、Complaint、Duplicate Debit。

常见误区：Gateway Accepted当作最终成功；把所有失败归因于余额不足；重复Retry重复计数；Payment Success用全体用户作分母；把技术失败直接写成信用坏账；只看件数不看金额。

判断方法：先看错误码/清算状态，再看账户匹配与设备，再看余额/现金流，最后才判断信用风险。

小练习与答案

10,000个到期账户，首扣成功6,300；3,700个首扣失败账户中2,300个在7天内Retry成功。求First Attempt Success、Retry Recovery、7日Payment Success。

答案：63%；2,300/3,700≈62.2%；(6,300+2,300)/10,000=86%。

第五部分【海外风控实操】

今日实操：Payment Failure Matrix × Smart Retry

所需数据：loan_id、user_id、due_date、due_amount、payment_attempt_id、attempt_no、attempt_time、payment_channel、bank_id、account_change_flag、device_change_flag、error_code、failure_type、settled_flag、settled_time、reversal_flag、duplicate_flag、fpd7、roll30、complaint、strategy_version。

步骤：固定Due/Eligible分母 → 首次尝试 → Error Code标准化 → Hard/Soft/Technical/Mismatch分类 → Retry → Settled Success@N → FPD/Roll → 成本/投诉。

SELECT
  payment_channel,
  failure_type,
  COUNT(DISTINCT loan_id) AS loans,
  AVG(first_attempt_success) AS first_success_rate,
  AVG(CASE WHEN first_attempt_success=0 THEN retry_success END) AS retry_recovery_rate,
  AVG(payment_success_7d) AS payment_success_7d,
  AVG(CASE WHEN fpd7_matured=1 THEN fpd7_flag END) AS fpd7
FROM payment_risk
GROUP BY payment_channel, failure_type;

分层：Channel × Bank × Error Type × Device Change × Bank Change × Score × Limit × New/Repeat。

内部阈值逻辑：First Attempt↓但Final PSR↑且Complaint稳定，可判断Retry有效但首扣链路需优化；First Attempt↓ + Technical Fail↑ = 技术黄灯；Bank Mismatch↑ + ATO/Fraud↑ = 风险红灯候选；Retry次数↑但Recovery不升 = 停止无效重试。

输出模板：Channel｜N｜Due Amount｜First Success｜Hard/Soft/Tech Fail｜Retry Recovery｜PSR@7｜FPD7｜Roll30｜Cost｜Complaint｜Action。

第二天复盘：先查清算延迟、Error Mapping、幂等与重复扣款，再看余额不足和信用风险；支付结果未落账前不把“处理中”标成失败。

第六部分【业务与产品】

风控 × 业务：不要把Payment Failure直接当Credit Failure

建议经营链固定为 Due → First Attempt → Failure Type → Retry → Payment Success@N → Cure/Roll → FPD/Vintage → EL/Margin。当首扣失败率上升时，先回答“是技术、账户、支付能力还是信用风险”，再决定策略；否则容易因为支付通道故障错误收紧准入。

风控 × 产品：银行卡/CLABE变更必须同时考虑可恢复体验与ATO风险

Technical Fail提供Retry/Fallback；余额不足可提供合规提醒和明确下次尝试时间；Invalid Account要求用户更新账户；New Device + Bank Change + High-value Drawdown/Repayment Anomaly触发Step-up。产品展示“处理中/失败/已成功”必须与清算状态一致，避免重复支付。

职责：产品负责状态、Retry和恢复路径；风控定义Hard/Soft/Mismatch及Step-up；数据维护Payment Funnel；研发保证幂等、清算回调和错误码；运营不得绕过高风险账户变更规则。
