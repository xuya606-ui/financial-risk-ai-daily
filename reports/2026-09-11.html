第三部分｜海外风控知识学习

今日主题：Fraud Thresholding & Cost-sensitive Decisioning｜欺诈阈值不是“抓得越多越好”

概念：Fraud Model通常输出风险分数/概率，但真正业务动作必须通过阈值把用户分成Allow、Step-up、Review或Decline。最佳阈值不是最大化Recall，而是最大化风险调整后的增量价值。

Net Fraud Decision Value ≈ Prevented Fraud Loss − Lost Good-Customer Margin − Review/Verification Cost − Complaint/Friction Cost

为什么重要：降低阈值会抓到更多Fraud，但同时误杀更多Good。Fraud prevalence很低时，即使FPR看起来不高，也可能产生大量误杀；因此必须同时看Fraud Capture/Recall、FPR、FNR、Precision、Approval、Review、Fraud Loss和Contribution Margin。

墨西哥现金贷七步案例

背景：首贷30天产品，50,000个成熟申请，真实Fraud prevalence为4%（2,000个Fraud），比较阈值A和更激进的阈值B。
数据：A拒绝6,000人，抓到1,560 Fraud：Recall 78%、FNR 22%、FPR约9.25%、Precision 26%。B拒绝9,000人，抓到1,800 Fraud：Recall 90%、FNR 10%、FPR 15%、Precision 20%。平均Fraud损失MXN900，Good获客后的风险调整贡献约MXN100。
现象：B多抓240个Fraud，理论多避免约MXN216k损失，但同时多拒2,760个Good，损失约MXN276k贡献，还未计入额外验证、投诉和流失成本。
拆解：Channel×Score×Device后发现，新增捕获主要来自Channel C新设备群；但B在稳定老设备、中高Credit Score段的False Positive显著增加。
根因：可以确认B提高Recall但降低Precision并提高FPR；是否真正更差需要把Fraud Loss、好客边际利润、Review与投诉成本全部计入，不能因Recall更高就直接下结论。
决策：高风险设备/团伙Segment采用B；稳定中低风险Segment保留A；A-B之间灰区改Step-up而非Hard Decline。
结果：至少观察两个成熟Fraud/FPD7 Cohort，要求Net Fraud Loss下降且Approval/Contribution Margin没有被不成比例侵蚀。

判断方法：先固定Fraud标签与成熟期 → 画Threshold Matrix → 同时算Recall/FPR/FNR/Precision → 估算每个阈值下Fraud Loss与Lost Good Margin → 按Segment做差异化动作 → Champion/Challenger验证。

常见误区：Recall越高模型越好；FPR低就认为误杀少；忽略Fraud Base Rate；不同成熟标签横比；把Review用户当Fraud；用未成熟Chargeback/Fraud Loss调阈值。

小练习与参考答案

A阈值Recall 80%、FPR 8%；B阈值Recall 92%、FPR 15%。在Good远多于Fraud的业务中，能否只看Recall选择B？

答案：不能。必须计算新增TP带来的Prevented Loss与新增FP造成的Lost Margin/Review/Complaint成本，并看Precision和Segment结构。

第四部分｜风控指标集合学习

今日升级4个高频反欺诈指标

今天把主字典中原本只有名称/简要定义的Fraud Capture Rate（Recall）、False Positive Rate（FPR）、False Negative Rate（FNR）、Precision/PPV升级为完整12段学习卡。下面给出核心摘要，完整卡见今日指标页。

指标精确公式核心判断
Fraud Capture / RecallTP ÷ (TP+FN)抓住全部真实Fraud中的多少；高并不等于净价值高
FPRFP ÷ (FP+TN)真实Good中被误判为Fraud的比例；需结合Good基数
FNRFN ÷ (TP+FN)真实Fraud中被漏掉多少；在同一二分类标签下=1-Recall
Precision / PPVTP ÷ (TP+FP)所有被判Fraud的人里到底有多少是真的；高度受Fraud Base Rate影响

第五部分｜海外风控实操

今日实操：Fraud Threshold Profit Matrix

所需数据：application_id、user_id、fraud_score、threshold_version、final_action、manual_review、stepup_result、mature_fraud_label、fraud_loss、approved_flag、disbursed_amount、contribution_margin、channel、credit_score_band、device_risk、limit_band、complaint_flag。

步骤：固定成熟Fraud标签 → 枚举候选阈值 → 生成TP/FP/TN/FN → 计算Recall/FPR/FNR/Precision → 计算Prevented Loss与Lost Good Margin → Channel×Credit Score×Device分层 → 设计Allow/Step-up/Review/Decline → Challenger验证。

Threshold Net Value = TP × Avg Preventable Fraud Loss − FP × Avg Good Margin − Review Cost − Friction Cost

SQL思路：

SELECT threshold_version,
       COUNT(*) AS n,
       SUM(CASE WHEN pred_fraud=1 AND fraud_label=1 THEN 1 ELSE 0 END) AS tp,
       SUM(CASE WHEN pred_fraud=1 AND fraud_label=0 THEN 1 ELSE 0 END) AS fp,
       SUM(CASE WHEN pred_fraud=0 AND fraud_label=1 THEN 1 ELSE 0 END) AS fn,
       SUM(CASE WHEN pred_fraud=0 AND fraud_label=0 THEN 1 ELSE 0 END) AS tn
FROM matured_fraud_sample
GROUP BY threshold_version;

Excel思路：使用TP/FP/FN/TN单元格直接计算Recall、FPR、FNR、Precision，并新增“Prevented Loss−Lost Margin−Review Cost”列做阈值排序。

阈值逻辑：不套统一行业阈值。内部黄灯示例：Recall提升但Precision持续下降且Approval/Margin同时恶化；红灯示例：新增捕获的Fraud Loss价值小于新增False Positive带来的好客损失。数值阈值均应根据自身成熟样本与经济模型设定。

异常诊断：标签成熟度 → Base Rate → Channel/Device Mix → Vendor/Data Drift → Threshold Version → Fraud Loss/Approval/Margin。

输出模板：Threshold｜N｜Fraud Base Rate｜Recall｜FPR｜FNR｜Precision｜Approval｜Review｜Prevented Loss｜Lost Good Margin｜Net Value｜Action。

第二天复盘：先复盘流量、模型分数分布、技术/Step-up失败和样本分流；Fraud Loss尚未成熟时不根据一天结果全量切阈值。

第六部分｜业务与产品

风控 × 业务｜Fraud Capture提升，不等于利润提升

经营链应从“模型抓到多少”升级为：Traffic → Fraud Score → Decision → Approval → Disbursement/EAD → Fraud Loss → Lost Good Margin → Review Cost → Contribution Margin。如果Recall从78%升到90%，却让FPR从9.25%升到15%，Good基数远大于Fraud时，误杀价值可能超过新增避免损失。风控周报建议把Recall、FPR、Precision、Approval和Net Fraud Loss放在同一屏。

风控 × 产品｜灰区优先Step-up，不要把所有高分都做Hard Decline

页面建议三层：低风险直接继续；灰区触发“为了保护账户安全，请完成一次额外身份验证”，优先Face/Liveness、银行卡姓名、可信设备或一次性验证；强身份冲突/团伙证据再Hard Decline。用户文案不暴露模型阈值、Rule ID、设备图谱或Fraud Score。

职责：产品负责Step-up流程和失败恢复；风控定义阈值、灰区与Hard Rule；数据负责TP/FP/FN/TN和Net Value；研发负责Decision Version、幂等、Fallback与日志；运营只能按标准Reason处理Review/Override，不得绕过强安全规则。
