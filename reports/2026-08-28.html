第三部分｜海外风控知识学习

今日知识：支付风险 Payment Risk——不要把“没扣到钱”全部当信用风险

概念：支付风险是从放款到账、银行卡/CLABE验证、自动扣款、主动还款到支付通道稳定性的一整套风险。它既包含技术失败，也包含账户欺诈、支付工具失效和客户现金流问题。

为什么重要：很多现金贷团队把FPD1上升直接理解为“客群变差”，但如果同一时间Auto-debit Success下降、支付服务商故障或银行返回码异常，真实原因可能是支付链路而不是信用风险。

还款失败 = 技术/通道失败 + 账户/银行卡问题 + 余额不足 + 客户主动不还 + 欺诈/账户接管

业务场景：自动扣款失败、CLABE/银行卡不匹配、支付服务商超时、银行返回“insufficient funds”、换卡后自动扣款失效、还款页面失败、支付凭证伪造。

常见误区：①所有DPD1都算信用恶化；②Payment Failure和Repayment Failure不分原因；③支付SDK升级后不看错误码分布；④只看成功率不看失败重试后恢复。

墨西哥现金贷模拟案例

背景：某首贷产品自动扣款通道升级。
数据：成熟样本18,000；Auto-debit Success 83%→69%；Payment Failure 7%→19%；FPD1 21%→30%；FPD3 17%→19%；FPD7 15%→15.8%。
现象：FPD1大幅恶化，但FPD7几乎稳定。
拆解：按支付返回码发现新增失败主要集中在Provider Timeout和Bank Routing Error，而不是Insufficient Funds；换到备用通道后二次扣款成功率达到72%。
根因：支付链路异常与FPD1跳升高度相关；是否完全由通道升级导致，可用切回旧版本/备用通道做对照验证。
决策：不收紧信用准入；恢复备用支付路由、增加智能重试，并把技术失败从信用FPD归因报表中单独拆出。
观察：Payment Failure、Retry Recovery、FPD1/3/7、投诉、Collection Rate和实际Bad Rate。

判断方法：FPD异常 → 支付错误码 → 自动扣款/主动还款分开 → 重试恢复 → 渠道/银行/版本拆分 → 再判断是否信用策略变化。

小练习与参考答案

某日FPD1从20%升到29%，但FPD7只从15%升到15.5%，同时支付超时从3%升到12%。先改信用策略还是支付链路？

答案：优先修支付链路和归因；信用策略不应因技术失败直接全量收紧。

第四部分｜风控指标集合学习

今日新增4张指标学习卡：Payment Failure Rate / Auto-debit Success Rate / Bank Account Match Rate / Repayment Success Rate

完整12段学习卡已同步到指标字典；下方保留核心说明、案例与诊断逻辑。

1. Payment Failure Rate｜支付失败率

是什么：进入支付执行的交易中，有多少没有成功完成。

为什么重要：是支付技术与用户现金流的同步指标；需要区分技术失败和余额不足。

Payment Failure Rate = 失败支付尝试数 ÷ 总支付尝试数

如何看：升高不一定意味着信用变差，必须拆Error Code、Provider、Bank、App Version。

案例：Failure 7%→19%、FPD1 21%→30%、FPD7基本稳定；新增失败集中Provider Timeout，说明技术原因更强。

诊断：Error Code → Provider/Bank → App/SDK Version → Retry Recovery → FPD3/7。

动作：技术型失败切路由/重试；余额不足才进入现金流/信用诊断。

误区：所有失败都算Insufficient Funds；按交易次数与按用户数混用。

拆分：Provider、Bank、Error Code、OS、App Version、自动扣款/主动还款。

预警：分钟/小时级技术基线 + 日级信用基线双层监控。

关系：Payment Failure → FPD1 → Retry Recovery → FPD3/7 → Collection。

2. Auto-debit Success Rate｜自动扣款成功率

是什么：到期自动扣款尝试中，真正扣款成功的比例。

Auto-debit Success = 成功自动扣款尝试 ÷ 有效自动扣款尝试

重要性：直接影响FPD1和早期催收压力，但受账户余额、银行卡状态、支付路由和银行限制共同影响。

案例：Success 84%→70%，但备用通道重试后可恢复到81%；此时先优化路由而不是扩大催收。

诊断：首次成功 → 返回码 → Retry Success → Bank/Provider → 用户余额/换卡。

动作：智能重试、备用路由、到期前提醒、换卡后的Mandate重建。

误区：只看第一次扣款；把自动扣款成功率当最终还款率。

关系：Auto-debit Success → FPD1 → Collection Load → Cure。

3. Bank Account Match Rate｜银行账户同名匹配率

是什么：提交用于放款/还款的银行卡或CLABE中，有多少通过借款人身份一致性校验。

Bank Account Match Rate = 通过账户持有人一致性校验的账户 ÷ 完成校验的账户

为什么重要：同时关联欺诈、代收款、账户接管和放款失败风险。

案例：Match由92%降到84%，但Fraud没有同步上升；拆解发现新银行接口对双姓/姓名顺序兼容差，属于技术/数据映射问题。

诊断：Name Normalization → Bank/Vendor → KYC Name → Device/ATO → Mature Fraud。

动作：技术型不匹配做标准化/二验；强身份冲突叠加高风险设备才升级拒绝。

误区：所有不匹配都判欺诈；未统一西班牙语重音/双姓规则。

关系：KYC Identity → Bank Match → Disbursement/ATO → Fraud Loss。

4. Repayment Success Rate｜还款成功率

是什么：应还或发起还款的订单中，最终成功完成还款的比例。

Repayment Success = 成功完成还款订单数 ÷ 到期/进入还款流程的有效订单数

重要性：是支付能力、支付体验与信用表现共同结果，必须与Collection、Cure和DPD结合。

案例：主动还款页面改版后Success 74%→66%，Payment Failure升高，但DPD7风险只轻微变化；说明产品/支付体验贡献较大。

诊断：支付入口 → Provider → Error Code → Retry → Cash Flow/DPD。

动作：优化还款路径、增加备用渠道、失败后保留账单状态和一键重试。

误区：只按支付尝试计算而不是订单；将部分还款直接视为完全成功。

关系：Repayment UX → Payment Success → DPD/Cure → Collection → Recovery。

第五部分｜海外风控实操

今日实操：FPD1异常的“信用 vs 支付”归因

所需数据：loan_id、due_date、dpd1/dpd3/dpd7、payment_attempt_time、payment_method、provider、bank、error_code、retry_count、retry_success、app_version、sdk_version、channel、score、limit。

步骤：①固定FPD成熟口径；②按自动扣款/主动还款拆分；③对Payment Failure按Error Code聚类；④计算首次成功与重试恢复率；⑤按Provider/Bank/App Version观察跳变；⑥再按Channel×Score×Limit判断剩余信用风险。

SELECT provider,error_code,COUNT(*) attempts, AVG(CASE WHEN payment_success=1 THEN 1.0 ELSE 0 END) success_rate, AVG(CASE WHEN retry_success=1 THEN 1.0 ELSE 0 END) retry_recovery FROM payment_attempts WHERE attempt_date BETWEEN :start AND :end GROUP BY provider,error_code;

阈值逻辑：支付失败相对历史基线突增且集中单一Provider/Error Code时，优先技术P0；若Failure正常但Insufficient Funds和FPD3/7同时恶化，再进入信用/现金流诊断。具体数值阈值使用内部历史，不采用统一行业标准。

输出模板：Provider｜Bank｜Error Code｜Attempts｜Success｜Retry Recovery｜FPD1｜FPD3｜FPD7｜App/SDK Version｜Root Cause｜Action。

第二天复盘：先看支付成功率和错误码是否恢复；FPD7/Bad未成熟前，不做全量信用收紧。

第六部分｜业务与产品

风控 × 业务：FPD1上涨，为什么不应该立刻降审批率？

因为FPD1同时受信用、支付通道和产品体验影响。若Payment Failure、Auto-debit Success或App Version同时发生明显变化，直接收紧审批会把技术事故转成“好客误杀”，造成放款、CAC摊薄和利润同时受损。

经营链路：Payment Route → Auto-debit/Repayment Success → FPD1 → FPD3/7 → Collection → Bad/EL → Contribution Margin。

建议所有FPD1日报同时带上Payment Failure、Retry Recovery和错误码Top10。

风控 × 产品：还款失败必须给用户“可恢复路径”

页面：不要只显示“还款失败”。明确区分“银行处理中”“余额不足”“支付通道暂不可用”“银行卡/CLABE需要重新验证”等可恢复状态。

交互：提供一键重试、备用支付方式、复制还款信息/参考号、到账状态刷新；换卡后重新建立必要授权。

规则：技术失败在内部标记Payment Technical Failure，不直接进入信用Reject/Bad标签；反复余额不足则进入现金流风险和催收策略。
