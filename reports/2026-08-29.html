2. 印度NBFC循环信贷草案争议：监管关注“借新还旧/债务循环”风险

发布日期：2026-08-28　性质：媒体报道/监管草案与行业反馈　风险：高

Reuters报道，印度Finance Industry Development Council要求RBI重新考虑针对非信用卡发行NBFC的循环信贷限制草案。监管草案倾向于仅允许Term Loan，核心担忧之一是可重复提款的循环额度可能被用于偿还既有债务，形成Debt Cycle；行业则认为全面限制也可能伤害MSME真实营运资金需求。该事项仍是草案和行业反馈，不是已经生效的最终规则。

影响：这一案例对海外现金贷的启示非常直接：循环额度/自动恢复额度不能只看“方便用户复借”，还要监控用户是否出现借新还旧、提款频率持续升高、可用额度一恢复就立刻用满、外部多头同步上升等Debt Cycling信号。

行动：循环额度产品增加Drawdown Frequency、Time-to-Redraw、Utilization、Active Lenders、Recent Inquiry、Repayment Source；高频“还款后立即再借”客群不要自动提额，应结合收入和现金流做差异化限制。

第三部分｜海外风控知识学习

今日知识：Credit Bureau × Multiple Borrowing｜征信与多头借贷策略

概念：征信策略的目的不是找一个“查询次数阈值”直接拒绝，而是把外部信用可见性、近期融资需求、活跃债务和偿付能力连接起来。

为什么重要：“征信查不到”可能是No-file、身份不匹配或接口故障；“历史账户多”也不等于当前多头。最值得关注的通常是近期新增查询 + 活跃Lender增加 + DTI/PTI上升 + 边缘Score + 高Limit的组合。

风险链：Bureau Hit → Recent Inquiry → Active Lenders / Balance → DTI/PTI → Score → Limit → FPD / Vintage / EL

墨西哥现金贷模拟案例

背景：12,000名首贷Bureau-hit申请用户，渠道C扩量。
数据：30天查询0-1次组FPD7=11%；2-3次=17%；4+次=27%；3+活跃Lender整体FPD7=24%；“4+查询 + 低Score + Limit≥MXN1,800”组FPD7=34%。
现象：Approval整体变化不大，但早期风险恶化。
拆解：Recent Inquiry × Active Lenders × Score × Limit × DTI，并排除Vendor超时和重复查询。
根因：风险更集中于近期资金需求快速上升与高额度组合，而不是所有历史多头用户。
决策：不做“查询≥4/多头≥3一刀切”；高查询+高DTI+边缘Score降额/二验；稳定收入、低额度组可Challenger。
观察：FPD3/7、金额FPD、MOB1 DPD30+、EL、Contribution Margin。

常见误区：把征信技术No-hit当No-file；把历史关闭账户算当前多头；不区分Hard/Soft Inquiry；同一机构重复查询不去重；把相关性直接写成因果。

小练习与答案

用户A历史有4个账户但仅1个当前活跃、30天无新查询；用户B有2个当前活跃账户，7天5次新查询，同时刚换设备。谁更值得优先二验？

答案：B。近期查询密度和账户/设备变化更能反映当前风险。

第四部分｜风控指标集合学习

今天新增四张完整12段学习卡：Bureau Hit Rate、Recent Inquiry Rate、Multi-Borrowing Rate、Application Velocity。

Bureau Hit Rate：看征信数据是否真正可用，必须把No-file、Identity Mismatch、Vendor Timeout分开。

Recent Inquiry Rate：看7/30天融资查询密度，需区分Hard/Soft、去重，阈值只能来自内部成熟历史。

Multi-Borrowing Rate：看当前同时持有多家活跃贷款的比例，重点是Active而不是历史账户总数。

Application Velocity：看User/Device/Phone/IP短窗口申请速度，适合识别资金压力和团伙/机器人风险，但要排除NAT和技术重复。

第五部分｜海外风控实操

今日实操：征信 × 多头 × 申请速度风险矩阵

字段：user_id、channel、bureau_hit、bureau_error、inquiries_7d、inquiries_30d、active_lenders、active_balance、verified_income、monthly_debt_payment、score_band、approved_limit、device_id、applications_30m、applications_7d、fpd3、fpd7、bad_flag、strategy_version。

步骤：① 分离技术No-hit/真实No-file；② 计算7/30天查询；③ 当前Active Lenders和余额；④ DTI/PTI；⑤ Application Velocity；⑥ Score×Limit分层；⑦ 对成熟样本计算FPD件数/金额与EL。

SELECT
  inquiry_band,
  lender_band,
  score_band,
  limit_band,
  COUNT(*) AS n,
  AVG(fpd7_flag) AS fpd7,
  AVG(monthly_debt_payment / NULLIF(verified_income,0)) AS dti
FROM matured_loans
GROUP BY inquiry_band, lender_band, score_band, limit_band;

判断：“近期高查询+多头+高DTI+边缘Score”才优先收紧；单一历史多头或单一查询次数不做全局硬拒。具体阈值必须使用内部成熟样本，不套行业统一值。

输出模板：Channel｜Bureau Hit｜Inquiry Band｜Active Lenders｜DTI｜Score｜Limit｜样本｜FPD3｜FPD7件数｜FPD7金额｜EL｜建议动作。

第二天复盘：先看Vendor可用性、查询/多头结构、Approval、Limit和FPD1/3；FPD7/Bad未成熟前不全量放松或收紧。

第六部分｜业务与产品

风控 × 业务：Approval没变，为什么FPD还会变差？

因为Approval只是通过比例，不代表通过用户结构没变。即使Approval始终32%，如果通过人群从“低查询+1家活跃Lender+MXN1,200额度”变成“4+查询+3家活跃Lender+MXN2,000额度”，件数和金额风险都会上升。

经营链：Channel → Inquiry / Multi-Borrowing → Score → Limit/EAD → FPD → EL → Contribution Margin。

因此日报建议增加“高查询通过占比、多头通过占比、这些人群的平均额度和金额FPD”，不要只报Approval。

风控 × 产品：征信不可用时必须有Fallback，而不是随机失败

新客：Bureau技术不可用时可重试/备用Vendor；仍不可用则进入低额度、补充验证或暂缓，不应把技术错误写成信用拒绝。

稳定复借客：可以在明确边界内使用内部历史还款、账户安全和收入数据做Fallback，但需要降低最大额度或缩短有效期。

真实No-file：可采用低额度首贷 + 收入/银行卡/KYC增强 + 后续真实表现逐步升级。

职责：产品负责状态解释和恢复路径；风控负责Fallback和额度边界；数据区分Vendor Failure/No-file/Identity Mismatch；研发负责重试和备用Provider；运营不得绕过高风险No-file策略。
