第三部分｜海外风控知识学习

今日主题：KYC Decision Waterfall & Identity Assurance｜KYC 决策漏斗与身份保证

概念：KYC 不应只有一个“通过/拒绝”结果，而应拆成 Start → Document Capture → OCR/Document Validation → Face/Liveness → Identity Match → Step-up/Manual Review → Pass/Fail。这样才能区分真实身份风险、用户流失和技术故障。

为什么重要：如果 KYC Completion 降低，可能是产品交互差、SDK崩溃、旧设备不兼容；如果 Identity Pass 降低，可能是客群风险上升，也可能是 Vendor 阈值变化。把所有失败都算成 Fraud，会造成好客误杀和 Approval 降低。

KYC Final Pass = Completed Identity Evidence × Valid Document × Liveness/Face Match × Policy/Step-up Outcome

墨西哥现金贷七步案例

背景：首贷 APP 更换人脸/活体 SDK，并扩大渠道 B。
数据：申请50,000；KYC Completion 78%→70%；Identity Verification Pass 91%→87%；Liveness Failure 5%→11%；Step-up Conversion 68%→44%；Approval 32%→27%；Confirmed Identity Fraud 2.8%→3.0%。
现象：审批明显下降，但确认身份欺诈只小幅上升。
拆解：Android旧版本 × Channel B × 新SDK 的活体技术失败最高；高风险Device/证件不一致群体的Fraud捕获才真正增加。
根因：可以确认技术失败与渠道结构同时变化；不能把全部KYC下降直接写成“欺诈增加”。
决策：技术失败提供重试/Fallback；文档冲突或强设备异常进入Step-up；明确身份冲突才Hard Fail。
结果：48-72小时看SDK Error/Completion；两个成熟Fraud Cohort后看Fraud Capture、FPR、Approval和Margin。

常见误区：活体失败=欺诈；KYC没完成=信用拒绝；SDK超时进入Fraud标签；只看Pass率不看Completion；新老客/设备版本混在一起。

判断方法：先拆技术与业务失败，再按 Vendor×App Version×Device×Channel×Document Type 拆；最终与 Fraud Outcome、Approval、Complaint 和 Cost 联看。

小练习与参考答案

KYC Completion 从80%降到68%，Liveness Failure 从4%升到13%，但成熟 Fraud 只从3.0%升到3.2%。第一动作是什么？

答案：优先排查 SDK/设备/网络技术链，不能直接全量收紧KYC。

第五部分｜海外风控实操

今日实操：KYC Funnel × Vendor/Device Root Cause Matrix

字段：application_id、user_id、channel、app_version、os_version、device_model、kyc_vendor、document_type、ocr_result、document_validation、liveness_result、face_match_score、stepup_flag、stepup_result、technical_error_code、final_kyc_result、fraud_matured、fraud_label、approval、complaint、strategy_version。

步骤：固定Eligible分母 → Start/Completion → OCR/Document → Liveness/Face → Step-up → Final Pass → Vendor×Device×Version → Fraud Outcome → Approval/Margin。

SELECT channel, kyc_vendor, app_version,
       COUNT(*) AS n,
       AVG(kyc_completed) AS kyc_completion,
       AVG(identity_pass) AS identity_pass,
       AVG(liveness_fail) AS liveness_fail,
       AVG(CASE WHEN stepup_required=1 THEN stepup_pass END) AS stepup_conversion
FROM kyc_funnel
GROUP BY channel, kyc_vendor, app_version;

阈值逻辑：不使用行业统一阈值。内部黄灯示例：Completion/Step-up 连续两个小时或两个批次跌出稳定区间且 Technical Error 同步升高；若 Confirmed Fraud 与 Identity Conflict 同时上升，再升级风控红灯。

第二天复盘：先看错误码、设备版本、Vendor SLA 和流量结构；Fraud 标签未成熟前不因单日 Pass 下降直接长期收紧。

第六部分｜业务与产品

风控 × 业务：KYC 下降先判断“风险变差”还是“系统变差”

经营看板建议固定：KYC Completion → Identity Pass → Liveness Failure → Step-up Conversion → Final KYC Pass → Approval → Confirmed Fraud → FPR → Contribution Margin。如果 Completion/Step-up下降但 Fraud 不升，优先查技术与产品体验；如果 Identity Conflict、Device Risk 和成熟Fraud同步升高，再做风险收紧。

风控 × 产品：KYC 页面必须给“可恢复失败”明确路径

OCR模糊、网络超时、SDK异常、光线不足等可恢复失败，应提供重拍、重试、Fallback Vendor 或人工复核；证件不一致、强团伙/设备冲突等高风险失败则不暴露具体Rule ID和阈值。产品负责恢复路径；风控负责Reason Taxonomy与Hard/Soft Fail；数据负责漏斗与Outcome；研发负责SDK/Fallback/日志；运营不得绕过强身份风险规则。
