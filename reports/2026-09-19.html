第三部分【海外风控知识学习】

今日主题：Thin-file & Bureau Coverage Governance｜薄征信与征信覆盖治理

概念：Thin-file 是真实信用历史较少；Bureau No-hit 是征信机构没有返回可用档案；Technical Fail 则是查询失败。三者完全不同。

为什么重要：把 No-hit 当“低风险”会放松准入，把Technical Fail当“高风险”会误杀；年轻客、新入职、现金经济和新进入正式金融体系的人群更容易出现Thin-file，因此需要用经过验证的替代数据补充，而不是自动提额或自动拒绝。

Query Success → Bureau Hit → File Depth → Inquiry Velocity → Alternative-data Coverage → Decision → FPD/Vintage → EL/Margin

墨西哥现金贷七步案例

背景：首贷产品扩大年轻客/自由职业者Channel C，同时接入新的SIC查询链路。
数据：月申请60,000；Bureau Query Success 98%→94%；Bureau Hit 82%→69%；Thin-file 18%→31%；30日Inquiry中位数1.4→2.6；Alternative-data Coverage 76%→91%；Approval 30%→34%；FPD7 14.5%→18.2%。
现象：审批增加，但早期坏账恶化；同时征信命中率显著下降。
拆解：Channel C×Thin-file×Limit≥MXN2,000 的FPD7约25%；稳定工资、低Inquiry的Thin-file约13%；Technical Fail样本风险并没有显著更高，但被大量拒绝。
根因：可以确认客群结构、Inquiry和额度变化与FPD恶化高度相关；不能把“Thin-file”直接写成唯一因果，也不能把查询失败等同信用差。
决策：Technical Fail走重试/Fallback；真实Thin-file使用收入、设备、账户活跃、历史付款等已验证信号做分层；High Inquiry + High Limit先降额；稳定低Inquiry Thin-file保留Challenger。
结果：等待两个成熟FPD7 Cohort，并看MOB1 DPD30+、EL/Loan、Approval、投诉和Contribution Margin。

常见误区：No-hit=好客；No-hit=坏客；查询失败算Thin-file；Inquiry越多一定越坏；替代数据覆盖越高就越好；使用未稳定/未授权数据直接影响拒绝。

判断方法：先拆技术与业务状态，再做 Channel×File Depth×Inquiry×Limit 分层，最后用成熟Outcome验证。

小练习与答案

10,000笔查询中9,500笔技术成功；技术成功里7,125笔有有效征信档案。Query Success和Bureau Hit分别是多少？

答案：Query Success=95%；Bureau Hit=7,125÷9,500=75%。不能用7,125÷10,000把技术失败混入Bureau Hit。

相关官方背景：CNBV｜SIC

第五部分【海外风控实操】

今日实操：Bureau Coverage × Thin-file Risk Matrix

所需数据：application_id、user_id、channel、bureau_vendor、query_status、bureau_hit、tradeline_count、oldest_tradeline_months、inquiries_7d、inquiries_30d、score_band、verified_income、alternative_data_coverage、approved_limit、approval_flag、fpd7、dpd30、maturity、strategy_version。

步骤：①拆 Technical Success/Fail；②仅在技术成功样本计算Bureau Hit；③定义Thin-file规则版本；④按Channel×Thin-file×Inquiry×Limit分层；⑤看Approval/FPD/Amount FPD/EL；⑥对Technical Fail和真实Thin-file制定不同动作。

SELECT
  channel,
  bureau_vendor,
  CASE WHEN query_status='SUCCESS' THEN 1 ELSE 0 END AS query_success,
  AVG(CASE WHEN query_status='SUCCESS' THEN bureau_hit END) AS bureau_hit_rate,
  AVG(CASE WHEN query_status='SUCCESS' AND bureau_hit=1 THEN thin_file_flag END) AS thin_file_rate,
  AVG(CASE WHEN fpd7_matured=1 THEN fpd7_flag END) AS fpd7
FROM bureau_risk_sample
GROUP BY channel, bureau_vendor;

内部预警：Query Success下降且所有风险Outcome稳定，优先技术黄灯；Bureau Hit下降、High Inquiry占比上升并伴随FPD/EL恶化，才升级风险黄灯/红灯候选。具体阈值必须使用内部历史基线，不冒充行业标准。

第二天复盘：先看Vendor SLA、超时/授权错误、重复查询；再看Channel Mix和Inquiry；深度坏账未成熟前不因一天No-hit上升就全量拒绝。

第六部分【业务与产品】

风控 × 业务：不要把“有征信/没征信”做成二元审批

业务链建议改为：Query Success → File Depth → Inquiry → Income/Device/Account → Approval → Limit/EAD → FPD/Vintage → EL/LTV。年轻或新入正式金融体系用户可能Thin-file但并非高风险；反过来，有完整征信但Inquiry突然升高的用户也可能正在进入多头借贷。

风控 × 产品：征信失败应该有“重试/授权/降级”路径

产品：对授权缺失、网络超时、Vendor失败提供重试或明确提示；不要把技术失败页面写成信用拒绝。风控：定义Thin-file与Inquiry Guardrail。数据：维护Query Success/Hit/Thin-file/Inquiry→Outcome。研发：记录Vendor/Error/Consent/Retry与幂等。运营：不能通过人工补录绕过高风险Inquiry或征信授权要求。
