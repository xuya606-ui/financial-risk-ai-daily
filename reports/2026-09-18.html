第三部分｜海外风控知识学习

今日主题：AML Transaction Monitoring & Case Prioritization｜反洗钱交易监控与案件优先级

概念：AML Transaction Monitoring 不是“规则命中越多越好”，而是把客户、国家/地域、产品、交易、设备、受益人/付款人等风险信号转换成高质量 Alert，再通过 Case Investigation 决定是否升级、关闭、持续监控或进行法定报告。

Risk Assessment → Scenario / Model → Alert → Triage → Case → Investigation → SAR / STR / ROIU or Close → QA → Feedback

为什么重要：Alert 数量过少可能漏风险；Alert 数量过多且质量低，会制造 Backlog、TAT上升和真正高风险 Case 延迟。FCA 9月17日启动的 EES 调查再次说明，风险评估、控制、治理、记录和监控是同一条监管链。

墨西哥现金贷七步案例（模拟）

背景：墨西哥数字现金贷 APP 对 SPEI 还款、第三方代还、异常账户变更和高频小额资金循环做 PLD/FT 交易监控；Rule Set V3 上线后新增“第三方付款人 + 高频入账”场景。
数据：月监控交易120,000笔；Alert Rate 2.8%→5.1%；Alert-to-Case 42%→29%；Case-to-ROIU/STR 8%→6%；P90 Case Aging 36h→82h；Backlog 420→1,150；高风险客户覆盖率基本不变。
现象：Alert 数量几乎翻倍，但真正升级 Case/法定报告的 Yield 下降，队列显著变老。
拆解：异常主要集中“老客、低金额、稳定设备、固定家庭成员第三方代还”，而真正高风险样本更多集中“新设备 + 新付款人 + 短周期多账户资金循环 + Bank Change”。
根因：可以确认 V3 引入后低风险 Alert 激增、Case Aging 恶化；但不能据此认定低金额第三方代还没有风险，需通过成熟 Case Outcome、QA 与调查证据评估规则边际价值。
决策：稳定老客/固定第三方付款人降级为监控或低优先级；新设备+新付款人+多账户循环保持高优先级；Case Queue 按 Customer Risk、Amount、Network、Velocity、Rule Severity 排序。
结果：连续2-4周观察 Alert Rate、Alert-to-Case、Case-to-ROIU/STR、P90 Aging、Backlog、高风险Case TAT、QA Error、确认可疑模式覆盖，确保“降量不漏高风险”。

常见误区：Alert=可疑交易；报告率越高越好；把全部低价值 Alert 自动清除；只按金额排序 Case；Case Aging 上升就简单加人而不修规则；不同规则版本直接比较。

判断方法：固定 Rule/Model Version → Alert 分母 → Yield → Case Aging/Backlog → Risk Segment → Outcome/QA → Net Investigative Value。

小练习与答案

某月120,000笔监控交易产生6,000个Alert，其中1,800个升级Case，成熟Case中120个最终提交法定可疑报告。Alert Rate、Alert-to-Case、Case-to-Report分别是多少？

答案：5.0%、30.0%、6.7%。如果 P90 Case Aging 同时由36h升至80h，应优先检查规则低质量扩量和队列优先级，而不是只看Alert总量。

第四部分｜风控指标集合学习

今日新增/复习4张完整学习卡：AML Alert Rate、Alert-to-Case Escalation Rate、Case-to-SAR/STR/ROIU Conversion Rate、AML Case Aging / Investigation TAT。以下为摘要，完整12段结构见今日指标页。

AML Alert Rate：反映监控规则/模型对交易或客户产生警报的密度，不是风险高低本身；应与 Rule Version、Yield、Backlog 同看。

Alert-to-Case：衡量 Alert 经过初筛后真正需要调查的比例，过低常提示规则噪声或 Triage 设计问题。

Case-to-Report：衡量成熟 AML Case 中最终产生 SAR/STR/ROIU 等法定可疑报告的比例；不同司法辖区报告名称和触发条件不同，不能把比例当“越高越好”。

Case Aging / TAT：衡量从 Alert/Case 产生到结案/报告的时效，P50/P90 与 Backlog、Severity 一起看，比单纯平均时长更稳健。

第五部分｜海外风控实操

今日实操：AML Queue Health × Rule Yield Matrix

所需数据：alert_id / customer_id / transaction_id / rule_id / rule_version / alert_time / case_id / case_created / case_closed / case_outcome / report_flag / customer_risk / country_risk / amount / channel / payer_account / beneficiary_account / device_id / velocity_features / analyst / qa_result。

操作步骤：统一 Alert/Case 去重 → 固定 Rule Version → 算 Alert Rate → Alert-to-Case → Case-to-Report → P50/P90 Case Aging → Backlog → Rule×Customer Risk×Channel×Network 拆分 → QA / Confirmed Pattern 复盘。

SQL思路：

SELECT rule_id, rule_version, COUNT(*) alerts, AVG(case_flag) alert_to_case, AVG(CASE WHEN mature_case=1 THEN report_flag END) case_to_report, APPROX_PERCENTILE(case_age_hours,0.9) p90_age FROM aml_monitoring GROUP BY rule_id,rule_version;

阈值判断：不使用行业统一阈值。内部示例：Alert Rate 上升但 Alert-to-Case、Case-to-Report 同时下降且 P90 Aging/Backlog 上升，定义为“低质量扩量黄灯”；高风险 Segment Case Aging 超 SLA 且报告/确认风险持续出现，定义为“队列红灯候选”。

异常诊断：先查 Rule/Data 版本 → 再看低风险噪声 → 再看高风险Case是否被延迟 → 最后决定 Rule Tuning、Priority、自动化或增员。

输出模板：Rule｜Alerts｜Alert Rate｜Alert→Case｜Case→Report｜P50/P90 Age｜Backlog｜High-risk Coverage｜QA Error｜Action。

第二天复盘：优先验证前一日调低优先级的 Segment 是否存在漏报风险，抽样检查被 Auto-close/低优先级的 Case，并检查高风险 Queue Aging 是否下降。

第六部分｜业务与产品

风控 × 业务：Fraud、KYC、AML 不应是三条孤立流水线

建议把全生命周期风险链统一成：获客/注册 → KYC/Device → 申请/授信 → 放款账户 → 还款付款人 → 账户变更 → 复借 → 逾期/催收 → AML/Fraud Case。例如“第三方还款 + 新设备 + Bank Change + 多账户循环”同时可能涉及 ATO、欺诈和 PLD/FT，不能只被某一个团队看到。
