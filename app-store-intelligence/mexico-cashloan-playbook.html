一、全生命周期流程图

建议把整个上架流程作为一个跨部门项目管理，而不是运营单点上传素材。

1

确定实际业务模式

先明确 APP 是直接放贷、导流/获客、撮合第三方贷款，还是同一 APP 内存在多个贷款方。该判断直接影响 Google Financial features declaration、牌照/证明材料、商店文案和审核解释。

2

锁定开发者账号主体

金融服务建议使用实际经营或可合理解释业务关系的公司主体。Google Play 对金融产品/服务要求使用 Organization developer account；Apple 的高监管行业也强调由提供服务的法律实体提交。

3

完成墨西哥主体/资质映射

把开发者账号主体、品牌方、实际运营方、合同主体、放贷/资金方、隐私责任主体、客服主体放到一张关系图中，并保存关系证明。

4

准备产品与商店披露

贷款期限、APR/本地等效年化指标、全部费用、代表性总成本、还款方式、客服、隐私政策必须与 APP 内真实产品和合同一致。

5

权限、SDK、数据合规扫描

在打包前完成 Manifest/entitlements、运行时权限、SDK 数据采集和第三方域名扫描，避免贷款 APP 使用商店禁止或高风险的敏感数据。

6

提交审核与可审查环境

准备稳定测试账号、可绕过 OTP/风控阻断的审核路径、Review Notes、贷款主体说明和必要证明材料。

7

发布后治理

每次费率、期限、主体、资金方、权限、SDK、隐私政策变化，都应触发应用商店影响评估，而不是只在版本发布时检查。

二、开发者账号申请

Google Play

组织账号

  • 金融产品/贷款业务选择 Organization account。
  • 准备公司法定名称、注册地址、官网、域名邮箱。
  • 准备 D‑U‑N‑S Number 及身份/组织验证材料。
  • 建立主管理员 + 备份管理员，避免单人控制。
  • 账号主体变更前先评估 APP 转移和验证风险。
Apple

Organization Membership

  • 合法实体名称必须可验证。
  • 准备 D‑U‑N‑S、官网、组织域名邮箱。
  • 申请人应有代表组织签署协议的权限。
  • Account Holder 只用于核心协议和权限管理。
  • 不要让外包公司长期持有核心开发者资产。
高风险

账号常见踩坑

主体与实际经营方完全无关联；官网为空壳页；公司名/地址不一致；多人共享主账号；关联历史违规账号；审核期间突然修改公司信息；用个人账号承载受监管金融业务。

三、墨西哥主体、资质与关系证明

核心原则：应用商店合规不能替代墨西哥本地金融合规。对于受监管金融机构，应能在 CONDUSEF 的 SIPRES 等官方体系核实主体状态；不同业务模式可能涉及不同的许可、注册或合同登记义务，需结合实际法律主体判断。

角色必须明确的问题建议证据
开发者账号主体谁向 Google/Apple 提交 APP？公司注册文件、D‑U‑N‑S、官网、授权
APP 品牌方商店展示品牌归谁？商标/品牌授权或集团关系
运营主体谁负责产品、营销、客服和运营？官网、服务协议、合作协议
合同主体用户与谁签贷款合同？合同样本、RECA 等适用登记信息
放贷/资金方谁真正向用户提供贷款？SIPRES/许可或注册信息、合作协议
费用收取主体利息/佣金由谁收取？费用表、RECO 等适用信息
隐私责任主体谁决定个人数据处理目的与方式？隐私声明、数据处理协议
客服/投诉主体用户向谁投诉与行权？客服渠道、UNE/相关投诉机制
推荐输出物：制作一张“7 主体关系图”，并给每条关系附证据链接。上架、申诉、主体变更时直接复用。

四、首次上架材料与商店文案

Google Play 必备

  • Category = Finance。
  • 最短与最长还款期限。
  • 最大 APR 或与当地法律一致的等效年化指标。
  • 代表性贷款总成本示例：本金 + 全部适用费用。
  • 完整隐私政策。
  • Financial features declaration。
  • 贷款方信息及其与开发者业务关系。
  • 如目标国家要求，上传有效许可证/证明。

Apple 必备

  • 显著披露贷款条款。
  • 最大等效 APR。
  • 付款/到期日或还款期限。
  • 个人贷款产品不得要求 60 天或以内全额还清。
  • 最高 APR 不得超过 Apple 指定上限。
  • 高监管金融业务准备主体与资质证明。
  • Review Notes 说明完整审核路径。
推荐商店描述结构

第一屏：产品是什么、谁提供服务、服务地区。
贷款参数：金额区间、期限、APR/等效年化、费用。
代表性示例：借款金额 → 利息/费用 → 总还款额。
主体信息：运营/放贷主体及必要注册信息。
支持信息：客服、隐私政策、官方网站。

严禁的“营销先行”做法

只写“低息”“秒批”“0 利息”而不披露条件；截图展示与真实授信不一致额度；用促销费率替代最高 APR；刻意隐藏服务费；商店写 90 天但 APP 实际 30 天；品牌名与合同主体完全断裂且无解释。

五、隐私、权限与 SDK 发布前审计

贷款高风险

敏感数据

Google Play 对个人贷款 APP 对联系人、照片等敏感用户数据有明确限制。发布前必须检查直接代码与第三方 SDK 是否访问这些数据。

四方对账

真实代码/网络行为 ↔ Google Data safety ↔ Apple App Privacy ↔ 隐私政策四方必须一致。

SDK 清单

归因、广告、风控、推送、客服、分析 SDK 都应记录版本、权限、采集字段、域名、数据去向与 Owner。

发布前技术扫描清单
  • AndroidManifest.xml / iOS entitlements。
  • 运行时权限触发页面和用户说明。
  • 所有 SDK 初始化行为。
  • 启动后前 60 秒的网络请求域名。
  • 后台采集位置、设备标识、通讯录/媒体等行为。
  • 删除账户后数据是否真正删除或按法律规则保留。

六、审核测试环境与 Review Notes

审核账号要做到“可稳定复现”

  • 测试账号长期有效，不依赖真实手机号收 OTP。
  • 不要让风控把 Apple/Google 审核设备直接拒绝。
  • 明确审核地区、测试手机号、测试身份证明或沙箱方案。
  • 审核人员可完整体验：首页 → 申请 → 报价/费用 → 合同 → 借款确认。
  • 若无法真实放款，要说明模拟环境边界。
Review Notes 推荐结构：业务模式 → 贷款提供方 → 测试账号 → 测试步骤 → 关键贷款披露页面 → 资质/关系证明 → 联系人。

七、版本更新时必须重新评估的变更

变更是否触发商店复核重点动作
APR/费用/期限必须同步商店描述、截图、代表性示例、合同
放贷/资金方必须更新 Financial declaration、主体关系和证明
品牌/公司主体必须评估账号转移、商店名称、合同和隐私
新增权限必须权限用途、Data safety/App Privacy、隐私政策
新增 SDK必须数据采集、第三方共享、权限和域名审计
仅 UI 微调视情况确认未改变贷款承诺和审核路径

八、拒审、下架与申诉 SOP

1

冻结继续提交

先停止无目的反复提审，保存拒审原文、政策编号、版本号、截图、审核时间。

2

分类根因

贷款政策 / 权限隐私 / 主体资质 / 元数据 / 无法审核 / 账号级风险。

3

找到证据差异

比较“政策要求、商店文案、APP 实际行为、合同、主体证明”五类证据，定位哪一处不一致。

4

先修复再申诉

若确有违规，优先修产品/权限/文案；不要把申诉当成绕过政策的渠道。

5

提交结构化申诉

说明政策点 → 根因 → 已完成修改 → 新版本 → 复核路径 → 截图/证明。只提交与该政策相关的证据。

申诉模板骨架

Issue：我们收到关于 [政策名称/条款] 的审核反馈。
Root cause：原版本在 [页面/权限/主体说明] 存在不一致。
Fix：已在版本 [x.x.x] 完成 [具体修改]。
Verification：审核人员可通过 [路径] 验证。
Evidence：附件包含 [截图/主体证明/政策映射]。
Request：请基于更新版本重新审核。

  • Financial features declaration 完成。

  • Review Notes 完整。

  • 费率/主体/SDK 变化触发复核机制已建立。

十、长期知识库维护规则

本手册不作为一次性文档。后续每次 Google Play、Apple、CONDUSEF 或墨西哥相关政策变化，都应更新：政策原文、发布日期、生效日、影响范围、旧规则、新规则、产品影响、研发影响、待办 Owner、验证结果。真实拒审案例应脱敏后回填到“拒审与申诉”章节。

重要：本页用于产品与应用商店合规工作管理，不替代墨西哥执业律师或当地监管机构的正式法律意见。不同公司主体和贷款模式可能适用不同监管要求。
