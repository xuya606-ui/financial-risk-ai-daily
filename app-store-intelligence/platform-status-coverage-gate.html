平台状态信号的“可覆盖范围”门禁

本专题服务于第 02、07、09 类知识：APP 上架与发布监控、长期运营治理、Google 审核监控。核心原则是：平台状态源只能在覆盖范围与当前异常对象匹配时，作为归因证据使用。

一、三项属性

coverage：该状态页覆盖哪些产品/接口，例如 Google Play Status Dashboard 当前主要覆盖 Play Billing、Publishing API、Play Integrity 等。

freshness：最后更新时间、时区、是否存在延迟。

authority：官方状态页、官方帮助页、控制台事实、第三方社区信号分别记录，不混为同一等级。

官方原文：Google Play Status Dashboard

二、禁止的错误归因

  • 状态页 No incidents ≠ 审核队列正常。
  • Publishing API 正常 ≠ Play Console 所有页面正常。
  • Build 已完成处理 ≠ 版本已进入正式审核。
  • 审核时间变长 ≠ 一定是人工审核或平台故障。

三、建议字段

platform / product_scope / status / checked_at_utc / source_url / coverage_note / incident_match / confidence_level / next_check_at

四、发布门禁

  1. 先判断异常对象属于平台状态页覆盖范围。
  2. 若不匹配，记录 PLATFORM_STATUS_NOT_CONCLUSIVE，转入 Build、审核生命周期、审核账号访问、自有后端四层排查。
  3. 若匹配，再核对时间窗口、地区、产品和官方 incident URL。
  4. 归因结论必须附官方原文入口，并保留检查时间。

五、对现金贷 APP 的落地

金融/信贷版本应将平台状态、Financial features declaration、Data safety/App Privacy、merged Manifest、SDK inventory、Mexico 主体与 RECA/PUR 证据分开冻结。任何一层不匹配时，不能用另一层状态替代。

Apple 工具链官方原文：App Store Connect Release Notes
