长期治理

核心原则：官方状态是事实层，不是万能解释

Google Play Status Dashboard 当前只覆盖部分 Play developer products，并且官方明确标注仍为试点。因此 No incidents 只能表示“已覆盖产品没有已知事故”，不能反向证明 Play 审核队列、人工审核或所有 Console 功能正常。Apple 侧应优先使用 App Store Connect 的 Build status、App/submission status、History 与 Webhook 事件还原实际状态。

归因树

层级判定依据建议状态动作
1. 平台事故官方状态页/官方公告与异常产品、时间窗口一致PLATFORM_INCIDENT_CONFIRMED冻结重复提交；记录 incident URL / start / end / affected product；恢复后再重试。
2. Build / Upload 处理上传成功但 build 长时间 Processing、Invalid Binary、Missing Compliance 等BUILD_PROCESSING_ISSUE先看 Build status；Apple 官方说明 build 若保持 Processing 超过 24 小时，可能出现问题，应联系支持。
3. 审核生命周期 / 队列已进入正式审核状态但 queue age 持续增长，官方状态页无匹配事故REVIEW_QUEUE_RISK保留 submission 不变；核对 last resubmission / planned release / support case。
4. 审核访问Demo account、OTP/MFA、KYC 测试数据、后端 review mode 不可用REVIEW_ACCESS_BLOCKED先恢复审核可达性，再在 Notes / Reply 中提供可重复验证路径。
5. 政策/声明Financial declaration、Data safety/App Privacy、贷款披露、权限或主体证据不一致POLICY_OR_DECLARATION_DRIFT做声明 Diff 与 Evidence Manifest 对账，修复后再提交。
6. 自有业务/基础设施仅自家 API、登录、KYC、OCR、合同或支付链路异常APP_BACKEND_INCIDENT走内部 SRE/业务故障流程，避免误报商店审核故障。
Apple 官方阈值

Build Processing 超过 24 小时：升级处理

Apple 的 App build statuses 帮助文档明确写明：如果上传的 build 保持在 Processing 状态超过 24 小时，可能出现了问题，应联系 Apple。这个 24 小时是可直接落到自动告警中的官方操作阈值，而不是内部猜测。

建议字段：build_uploaded_at / build_processing_started_at / build_status / processing_age_hours / apple_support_case_id / status_checked_at。当 processing_age_hours > 24 且状态仍为 Processing 时，进入 APPLE_PROCESSING_ESCALATE。

Apple 可观测性

History + Webhook 做事实时间线

Apple App Store Connect History 会记录版本状态、状态变化时间和发起人；Webhook 可以自动推送 build upload、beta build、App version、Apple-hosted asset pack 等状态变化。建议把 Webhook 当实时流、History 当审计补偿源，形成单一事实时间线。

Google 可观测性

Status Dashboard 仅做“已覆盖产品”的事故事实层

建议在 Google 审核 Dashboard 增加 platform_status / platform_status_checked_at / affected_product / incident_url / official_lifecycle_state / queue_age_hours。如果状态页 No incidents，标记 PLATFORM_INCIDENT_NOT_CONFIRMED，不要标记 PLATFORM_HEALTHY，因为官方明确说明该 Dashboard 尚未覆盖全部 Play developer products。

自动化判定建议

优先级顺序：官方事故 → Build/Upload → 官方审核状态 → Review Access → Policy/Declaration → 自有后端。只有在平台官方事故与时间窗口、产品范围匹配时，才使用“平台事故”作为主因。任何 IP、ASN、设备、国家或 review account Session 特征都只能作为审核行为辅助信号，不能用于声称识别 Google/Apple 审核人员身份。

platform / app / version / build / submission_id / event_time / official_lifecycle_state / build_status / queue_age_hours / platform_status / affected_product / incident_url / review_access_health / declaration_diff / backend_health / attribution_state / confidence / owner / support_case_id / evidence_sha256
