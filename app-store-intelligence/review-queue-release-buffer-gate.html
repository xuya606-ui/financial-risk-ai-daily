核心原则：审核耗时是“发布风险信号”，不是审核人员身份信号，也不是机器/人工审核的单变量判定依据。先以平台官方生命周期状态作为事实层，再用队列时长、审核账号行为和服务端事件做辅助分析。

1. 为什么要做发布缓冲

Google 官方口径

Google 长期支持口径说明，部分 App 可能被纳入扩展审核，审核时间可能达到 7 天或更长；审核过程中继续提交版本、商店页、价格/分发等变更，可能导致审核重新开始。对金融、贷款等高风险业务，不能继续按“过去通常 1–2 天”安排硬上线日。

2. 建议数据模型

字段用途
submission_id版本/提交唯一标识。
submitted_at本轮真正进入审核队列的时间。
official_review_state平台事实状态，例如 In Review / Approved / Rejected；优先级高于行为推断。
queue_age_hours当前审核队列时长。
last_change_at最近一次影响审核的控制台/商店/二进制变更。
last_resubmission_at最近一次重新提交；用于识别是否可能重新计时。
planned_release_at业务计划发布时间。
buffer_hours计划发布时间与提交时间之间的缓冲。
support_case_id超过内部阈值后的支持工单号。
managed_publishing是否通过 Managed Publishing 把审核完成与正式上线解耦。
finance_app是否金融/信贷高风险业务，用于更早触发预警。

3. 内部阈值（不是平台 SLA）

状态建议阈值动作
NORMAL0–72h正常观察，不因焦虑做无必要变更。
WATCH72–168h复核是否有待处理政策项、Review Access、声明或材料问题；冻结非必要控制台变更。
ESCALATE>168h进入支持工单/升级路径；保留提交截图、状态、Activity Log、最新变更时间和 package 信息。

以上 72h/168h 是内部运营阈值，用来做发布风险治理，不代表 Google 或 Apple 承诺的审核服务等级。

4. 金融/信贷 App 发布门禁

建议 P0

对墨西哥现金贷 App，关键版本建议至少在业务硬发布时间前 T-7 送审；大型 KYC、借款链路、权限、SDK、主体/资质或商店披露变化建议进一步提前。审核未完成时，不要为了“催一下”反复提交相同或无关版本。

送审前先锁定：Financial features declaration、商店贷款披露、merged Manifest/SDK、审核账号、OTP/KYC 测试数据、合同与隐私入口。审核通过后再使用 Managed Publishing 或灰度发布控制真正上线时间。

5. Dashboard 规则

建议增加 review_queue_state、queue_age_hours、release_buffer_remaining、resubmission_risk、support_escalation_state 五个核心指标。只有在平台进入正式审核窗口后，才运行机器审核 vs 人工审核概率模型；排队时间变长本身不能提高“人工审核概率”。

推荐告警：T-7 未送审、queue_age >72h、审核中发生新变更、buffer < 48h 且仍 In Review、>168h 无 support_case_id。

6. 处置 Runbook

  1. 确认当前官方状态是否真的为 In Review，而不是 Draft / Changes not sent / Managed Publishing 等其他状态。
  2. 检查近 7 天是否提交过新 APK/AAB、商店页、价格、地区、App Content、Data safety 或金融声明等变更。
  3. 确认审核访问账号、OTP/MFA、KYC 测试数据和后端审核环境仍可用。
  4. 如业务无必须修复的缺陷，冻结非必要修改，避免潜在重新计时。
  5. 超过内部 ESCALATE 阈值后建立支持工单，并附 package、versionCode、提交时间、Activity Log、截图与业务发布日期。
  6. 审核通过后用 Managed Publishing/灰度发布控制正式上线，不把“审批完成时间”强绑定为“业务发布时间”。
