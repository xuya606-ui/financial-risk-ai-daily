APP STORE INTELLIGENCE · RELEASE EVIDENCE

送审证据指纹门禁

把每一次 Google Play / Apple App Store 送审的二进制、商店声明、贷款配置、主体证据、隐私/SDK 与审核访问状态冻结为同一份不可混用的证据快照，避免拒审、申诉和审计时引用了错误版本的材料。

正式知识库首页长期知识库合规工作台模型字段门禁申诉
定位：这是内部治理方法，不是 Google 或 Apple 明文要求的新政策。它把平台已经要求开发者保持准确的 Data safety / App Privacy、金融声明、审核材料和实际构建版本绑定到同一个 submission_evidence_sha256，用于发版、审核、申诉和事后复盘。

一、为什么需要“证据指纹”

版本一致性

拒绝“跨版本拼证据”

同一个 App 的 Build、SDK、权限、Store listing、贷款条款和资金方都可能在不同版本间变化。申诉时如果拿 vN 的二进制配 vN-1 的 Data safety、截图或合同，很容易形成新的不一致。

Google Data safety 官方原文 ↗Apple App Privacy 官方原文 ↗
金融/信贷

把声明与真实产品锁定在同一时点

Google 的 Financial features declaration、贷款主体/合作机构、商店页披露和真实产品能力应一致。证据指纹将声明快照与实际贷款配置、资金方、合同主体、期限/APR/费用一并冻结。

域建议字段目的

三、门禁状态

EVIDENCE_MATCHED

构建、商店声明、贷款配置、主体/合同、隐私/SDK 与审核访问材料全部指向同一版本、同一时点。

EVIDENCE_DRIFT

任一关键材料发生变化但未重新生成证据指纹，例如升级 SDK 后 App Privacy 仍引用旧快照。

MISSING_CRITICAL_ARTIFACT

缺少 P0 证据，例如最终 merged Manifest、Financial features declaration、资金方关系、RECA/合同或审核账号健康检查。

READY_FOR_APPEAL

拒审发生后，能够从 submission_id 反查唯一证据指纹和对应 Build，所有解释、截图和修复证明均绑定该指纹。

四、拒审/申诉怎么用

申诉材料首页先写 submission_id + version/build + submission_evidence_sha256；然后按“政策点 → 根因 → 修改 → 精确路径/截图 → 官方证据 → 请求重新审核”的顺序组织。这样可以明确告诉审核方：当前申诉引用的是哪个 Build、哪个声明版本、哪个贷款配置与哪个主体证据，避免用旧截图或旧合同解释新版本。

五、建议自动化

CI 在 release candidate 生成后自动输出 canonical JSON → 计算 SHA-256 → 保存到制品库；送审前由合规工作台验证所有关键字段非空、政策证据未过期、商店声明 Hash 与控制台快照一致。任何 SDK、权限、资金方、条款、主体、Store listing 或隐私声明变化都强制重新生成证据指纹。

推荐最小输出：submission-evidence/{platform}/{version}/{build}/manifest.json、manifest.sha256、截图/声明快照索引、官方来源索引。
