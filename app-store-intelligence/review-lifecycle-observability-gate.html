STORE REVIEW LIFECYCLE OBSERVABILITY · 2026-09-12

审核生命周期可观测性门禁

用 Google Play 官方 ReleaseLifecycleState 与 Apple App Store Connect 状态/Webhook 做一手状态锚点，再叠加内部审核 Session 行为分析。目标不是“猜审核员”，而是把送审、在审、通过、拒审、发布的时间线自动化、可审计。

核心原则：平台官方状态是“审核生命周期真值源”；内部 Session、页面停留、输入/返回、API 密度等只用于推断审核访问行为。不要用 IP、ASN、国家或设备单独判断 Google/Apple 审核人员身份。

01｜Google Play：ReleaseLifecycleState 直接接入 Dashboard

官方 API

机器可读生命周期

Google Play Developer API 的 applications.tracks.releases 返回 release summary，并提供 releaseLifecycleState。可直接用于版本级审核时间线。

Google 官方 API 原文 ↗
状态锚点

审核关键状态

DRAFT → NOT_SENT_FOR_REVIEW → IN_REVIEW → APPROVED_NOT_PUBLISHED / NOT_APPROVED → PUBLISHED。其中 IN_REVIEW 是正式审核窗口的重要一手锚点。

ReleaseLifecycleState ↗
易混淆

审核状态 ≠ 灰度状态

不要把旧发布接口中的 draft / inProgress / halted / completed 当作审核生命周期；这些更偏发布/灰度状态。Dashboard 必须分开建模。

Google Tracks API ↗
高风险误判：如果把 staged rollout 的 inProgress 解释成“Google 正在审核”，会把审核开始时间、审核耗时以及 machine/human Session 窗口全部算错。正式审核概率模型建议以 releaseLifecycleState=IN_REVIEW 或 Console 明确在审状态作为窗口锚点。

02｜Apple：状态历史 + Webhook 自动收集

官方状态

App / Submission Status

App Store Connect 提供版本和 submission 状态，可区分准备提交、等待审核、审核中、待开发者操作、拒审、可发布/已发布等生命周期。

字段建议值 / 说明

04｜事件处理建议

Google

每 5–15 分钟轮询活跃送审版本的 release lifecycle；发生状态变化立即写入 append-only event table。发布完成后降低频率。

Apple

Webhook 为主、History/状态查询为补偿。接收端校验 Secret/签名机制、去重 event、处理乱序并保留原始 payload 摘要。

告警

IN_REVIEW 超 SLA、NOT_APPROVED、审核账号登录失败、状态回退、Webhook 连续失败、官方状态与内部结果不一致均进入告警。

05｜发布治理 Checklist

□ Google Play Developer API 服务账号/权限已按最小权限配置；□ 活跃 release 的 lifecycle polling 已启用；□ Apple Webhook 已配置、Secret 已安全保存且 Ping 测试成功；□ 状态事件表不可覆盖历史；□ Google rollout status 与 review lifecycle 分字段；□ 正式审核窗口只在官方“在审”状态后用于 machine/human 分析；□ Review result 与拒审材料自动归档；□ Dashboard 展示“官方状态 / 内部概率”两套标签，禁止混写。

06｜对墨西哥现金贷 APP 的价值

把平台状态与审核账号行为对齐后，可以更准确回答：送审后多久真正进入审核、审核账号是否成功完成 KYC→额度→费用/APR→合同→隐私/删除路径、拒审发生前审核最后查看了什么、不同版本/材料的审核时长是否异常。它应服务于合规证据和发布质量复盘，而不是规避平台审核。
