GOOGLE PLAY · POST-DEADLINE OPERATIONS

Google Play 执行后验证 Runbook

把政策截止日后的工作从“我们应该已经合规”变成“逐包验证、可观测、可追溯”。适用于 Target API、Play package 注册、Billing Library 等有明确执行日期的门禁。

2026-09-01 新增长期知识

为什么需要“执行后验证”

政策到期并不等于风险自动消失。截止日前要做的是升级、提审、申请延期；截止日后要做的是验证 Play Console 实际状态、新用户可发现性、提交门禁、延期范围与生产稳定性。尤其 Target API 规则同时影响“新 APP/更新是否可提交”和“旧 APP 对更高 Android 版本新用户的可发现性”。

01｜统一状态机

PRE_DEADLINE 截止日前，仍有整改窗口 ↓ ENFORCED 已进入正式执行日期 ↙ ↘ EXTENDED COMPLIANT 官方延期 已满足要求 ↓ ↓ COMPLIANT MONITORING ↘ ↙ MONITORING 若发现提交受阻 / 可发现性受限 / Console 警告： RESTRICTED → REMEDIATING → COMPLIANT
原则：不要用“代码已改完”作为最终状态。最终状态应以 Play Console 实际提示、可提交状态、设备/新用户可发现性和生产监控共同确认。

02｜执行后逐包验证

A

Console 状态

记录 target API、policy status、extension、package registration、签名与发布轨道。对每个 APP 截图/导出证据。

B

提交能力

对计划更新版本确认构建满足当前门槛，并检查 Play Console 是否出现提交阻断或合规提示。不要通过故意提交不合规包来“测试”。

C

新用户可发现性

对旧 target APP，结合 Play Console 可用设备/分发状态及干净账号/新系统版本进行抽查，确认是否出现可发现性限制。

D

延期真实性

保存 extension 的适用 APP、适用范围、截止日期和 Console 证据。不要把“可申请延期”理解成所有场景自动获得延期。

E

生产回归

API 升级后继续观察 OTP、KYC、OCR/相机、文件选择、Push、Deep Link、WebView、后台任务、风控/归因 SDK。

F

24h / 72h 复盘

对崩溃、ANR、登录/KYC 转化、审批漏斗、关键权限异常和渠道转化进行两次固定复盘。

03｜证据字段

字段说明
app_name / package_name唯一识别 APP
version_name / version_code当前生产与下一提交版本
target_sdk / compile_sdk当前技术门槛
policy_statusPlay Console 当前政策状态
extension_status / expires_at是否延期、何时到期
discoverability_check新用户/高版本系统可发现性抽检结果
submission_gate下一版本是否满足提交门槛
sdk_regression_status关键 SDK 回归结果
evidence_url / screenshot_atConsole 截图、日志或证据位置
owner / remediation_eta负责人和整改计划

04｜Dashboard 指标

合规覆盖率

target_api_compliance_rate = 已合规 APP / 全部需管理 APP。

延期依赖率

extension_dependency_rate = 仍依赖延期 APP / 全部需管理 APP。

受限 APP 数

记录 submission blocked、discoverability restricted、policy warning 三类事件。

整改时长

time_to_remediate：从发现执行后问题到恢复 COMPLIANT 的小时数/天数。

升级回归异常率

API 升级后登录、KYC、崩溃、ANR、关键 SDK 异常的版本对比。

证据完整率

每个 APP 是否具备 Console 状态、版本、签名、延期、验证时间和 Owner 的完整记录。
