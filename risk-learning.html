今日知识：设备风险与团伙欺诈图谱

一句话：设备风险不是判断“手机好不好”，而是识别User、Device、Phone、Bank/CLABE、IP、证件之间的异常复用和关系网络，发现单笔看起来正常、整体却高度关联的团伙。

为什么重要：传统单笔规则容易漏掉团伙；图谱可以在KYC、申请、提款前复核和账户接管阶段提供领先风险信号。

共享设备率 = 关联≥2个用户的设备数 ÷ 活跃设备数
节点度 = 某设备/银行卡/IP关联的不同用户数
组件Bad Rate = 连通组件内Bad成熟用户数 ÷ 组件内成熟用户数

墨西哥现金贷模拟案例

背景：首贷欺诈率上升，但单笔KYC、人脸通过率稳定。
数据：10,000申请；确认欺诈率3.2%→5.1%；设备一对多率6%→11%；同一CLABE关联≥3用户占比1.1%→3.8%；高风险组件FPD7 34%，全量14%。
现象：单笔身份校验没有明显异常，但共享设备+共享银行卡网络快速增长。
拆解：渠道C×低端Android×新手机号×同CLABE多用户的风险最集中。
根因：图谱关联与欺诈高度相关，但必须排除家庭共享设备、代理渠道代操作等合法场景；相关性不能直接写成因果。
决策：高风险多节点组合进入二次KYC/人工审核；单一共享设备不直接硬拒；提款前再次检查设备与银行卡变化。
观察：至少等FPD7/欺诈标签成熟，同时看Approval、误杀率和申诉率。

判断方法：User–Device–Phone–Bank–IP建图 → 节点度/组件大小 → 叠加Bad/欺诈标签 → 合法共享白名单 → 多信号组合升级风险。

常见误区：一对多设备直接拒绝；公共Wi-Fi/家庭设备与团伙混淆；标签未成熟就训练；只看设备ID而忽略多跳银行卡/IP/手机号关系。

今日小练习与参考答案

设备A关联4个用户，但4人不同银行卡且地址相同；设备B关联3个用户，3人共用同一CLABE且20分钟内集中申请。哪个优先审核？

答案：B，“共享收款账户 + 高频申请”比单一家庭共享设备更像团伙信号。

今日指标：FPR / FNR / Lift / Gini

FPR：真正好客中被误判为坏/欺诈的比例，FP/(FP+TN)，重点看误杀。

FNR：真正坏/欺诈中被漏掉的比例，FN/(FN+TP)=1-Recall，重点看漏放。

Lift：某高风险分段的Bad/Fraud Rate ÷ 全量Bad/Fraud Rate，回答模型是否把风险集中到了前部。

Gini：排序能力指标，常见关系Gini=2×AUC−1；不等于概率校准，也不等于利润。

关键：FPR/FNR必须转换成业务成本：误杀利润、漏欺诈损失、人工审核成本，再选择阈值。

今日实操：设备团伙图谱挖掘

必备字段：user_id、device_id、phone_hash、bank_account_hash/CLABE、IP、ID_document_hash、apply_time、channel、score、approval、disbursement、fraud_label、dpd7。

操作步骤：哈希/清洗节点 → 建User–Device/User–Bank/User–IP边 → 统计7/30天节点度和共现速度 → 构建连通组件 → 叠加成熟欺诈/FPD → 渠道×Score×组件大小拆解 → 形成二验/审核/拒绝策略。

SELECT device_id, COUNT(DISTINCT user_id) users, COUNT(*) apps FROM applications WHERE apply_date >= CURRENT_DATE - INTERVAL '30 day' GROUP BY device_id;

阈值：不要使用“设备≥2用户即拒绝”。示例可先测试“设备≥3用户且共享银行卡≥2”或“同CLABE≥3用户且30分钟高频申请”作为风险升级信号；阈值需用内部标签校准。

复盘：次日先看规则命中、人工审核量、Approval和申诉；欺诈/FPD结论等待成熟。

今日业务：为什么Approval稳定，欺诈损失仍会突然上升？

Approval只是漏斗结果。即使通过率一直30%，通过客群内部的设备团伙、高额度、共享银行卡占比发生变化，也可能使欺诈金额与EL恶化。

业务看板：Approval × 高风险设备占比 × Fraud Rate × 金额Fraud/Bad × EAD × Contribution Margin。Approval稳定、损失上升时先拆渠道/图谱/额度，不要直接认定“模型整体失效”。

今日产品：中风险设备用户采用Step-up Verification

低风险→正常授信；中风险→额外安全验证（重新活体、银行卡同名、OTP、短冷静期）；高风险/强团伙证据→拒绝或人工审核。单一共享设备不应成为唯一硬拒原因，多信号组合才升级风险。

职责：产品负责二验状态和解释；风控定义触发；数据监控二验→Approval→Fraud/FPD→申诉；研发保证关系查询实时可用与策略回滚；运营不得绕过高风险二验。
