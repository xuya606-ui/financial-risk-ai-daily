今日知识：Payment Risk｜支付风险

一句话：还不上与扣不到不是同一件事。支付风险要把技术/通道失败、账户问题、余额不足、主动不还和欺诈分开。

为什么重要：FPD1很容易受到支付SDK、Provider、银行路由和换卡影响。如果Payment Failure大幅跳升但FPD7几乎稳定，直接收紧信用准入往往是错误归因。

还款失败 = 技术/通道失败 + 账户/银行卡问题 + 余额不足 + 客户主动不还 + 欺诈/ATO

墨西哥现金贷模拟案例

背景：首贷14天产品升级支付SDK。
数据：18,000成熟订单；Auto-debit Success 83%→69%；Payment Failure 7%→19%；FPD1 21%→30%；FPD3 17%→19%；FPD7 15%→15.8%。
现象：FPD1显著恶化，但深度风险几乎不变。
拆解：Error Code显示新增失败集中Provider Timeout和Bank Routing Error，Insufficient Funds基本稳定。
根因：支付通道异常是更强候选原因；备用通道对照可进一步确认因果。
决策：恢复备用路由、智能重试；技术失败从信用FPD归因中单列，不全量收紧信用策略。
观察：Payment Failure、Retry Recovery、FPD1/3/7、投诉和Collection Load。

判断方法：FPD异常 → 支付错误码 → 自动扣款/主动还款分开 → 重试恢复 → Provider/Bank/App Version → 再判断信用结构。

小练习与答案

FPD1从20%升到29%，FPD7只从15%升到15.5%，支付超时从3%升到12%。先改信用还是支付？

答案：优先修支付链路和归因，不应因技术失败全量收紧信用准入。

今日指标：Payment Failure / Auto-debit / Bank Match / Repayment Success

Payment Failure Rate：支付尝试失败比例，必须拆Error Code、Provider、Bank和版本。

Auto-debit Success Rate：到期自动扣款成功比例，建议同时看首次成功和重试后的最终D+1成功。

Bank Account Match Rate：银行卡/CLABE持有人与借款人身份一致的比例，需要处理双姓、重音符号和Vendor规则差异。

Repayment Success Rate：到期/进入还款流程的订单中最终成功还款比例，需区分Full/Partial/Technical Pending。

今日实操：FPD1异常的“信用 vs 支付”归因

字段：dpd1/dpd3/dpd7、payment_method、provider、bank、error_code、retry_count、retry_success、app_version、sdk_version、channel、score、limit。

步骤：固定FPD成熟口径 → 自动扣款/主动还款拆分 → Error Code聚类 → 首次成功/重试恢复 → Provider/Bank/版本跳变 → Channel×Score×Limit剩余风险。

Payment Failure ↑ + Error集中单一Provider + FPD7稳定 → 先技术；Failure正常 + Insufficient Funds/FPD3/7同时恶化 → 再信用

复盘：第二天先看支付成功率和错误码是否恢复；深度风险未成熟前不全量调信用策略。

今日业务：FPD1上涨为什么不应立刻降审批率？

因为FPD1同时受支付通道、还款体验和信用影响。Payment Failure或SDK版本变更如果与FPD1同步跳升，直接收紧Approval会把技术事故变成好客误杀。

经营链路：Payment Route → Payment Success → FPD1 → FPD3/7 → Collection → Bad/EL → Contribution Margin。

今日产品：还款失败要有“可恢复路径”

用户侧区分“银行处理中”“余额不足”“支付通道暂不可用”“银行卡/CLABE需重新验证”等状态；提供一键重试、备用支付方式、到账状态刷新和必要的参考号。内部技术失败单独标记，不直接写入信用Bad标签。

职责：产品负责失败状态和恢复；风控分离信用/支付归因；数据维护Error Code→Retry→DPD；研发负责Provider Fallback与幂等；运营负责异常通知和投诉分流。
