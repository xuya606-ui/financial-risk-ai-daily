今日知识：Reject Inference｜拒绝推断

一句话：历史上被拒绝的人没有真实还款结果，因此训练模型时会出现“只看通过用户”的选择偏差；Reject Inference就是尝试估计被拒客群的潜在好坏表现。

为什么重要：现金贷策略越严格，训练样本越不像完整申请人群。当新策略向边缘Score扩张时，旧模型最容易低估未知区域的风险。

目标：估计 P(Bad | X, Reject)，或通过加权/随机样本等方式校正批准样本的Selection Bias

常见方法：Parceling、Augmentation/Weighting、Fuzzy Augmentation、随机Reject Sample/Challenger。所有推断标签都只是估计；受控随机批准一小部分边界客群能提供最有解释力的真实标签，但要限制额度与风险。

墨西哥现金贷模拟案例

背景：旧策略Approval=28%，团队计划通过新模型提升到34%。
数据：边缘Score段占全部申请12%，历史仅2%被随机通过；旧批准客FPD7=14%，边缘随机通过组FPD7=24%。
现象：只用旧批准样本训练会低估边缘Score风险。
拆解：Channel×Score×Limit后发现，边缘段中的低Limit+收入可验证组FPD7=17%，高Limit+近期多头组FPD7=31%。
根因：历史选择机制造成标签空白，而不是“所有拒绝客都坏”。
决策：边缘Score×低Limit设置5%-10%随机Challenger（内部示例），高风险组合继续拒绝；模型训练使用样本权重并用真实Reject Sample校准。
观察：等待FPD7并继续追MOB1 DPD30+，同时看Approval、EL和Contribution Margin。

常见误区：拒绝客全部标坏；推断标签当真实标签；策略改版后仍沿用旧选择机制；随机样本太小；实验不限制额度。

判断方法：Approval×Score分布 → 标签空白区 → 历史误批/随机样本 → 设计低风险Reject Sample → 真实标签校准 → 模型/策略评估。

小练习与参考答案

某Score段历史几乎全部被拒，但模型显示PD=9%，能直接用于额度策略吗？

答案：不能。该区域缺真实表现标签，PD可能受选择偏差影响，需先通过受控Reject Sample/Challenger或稳健推断方法验证。

今日指标：Disbursement / Cost of Funds / APR-CAT / ROI

Disbursement Rate：进入放款执行的订单里最终成功到账多少；下降先查支付/CLABE/通道，不要先怪风控。

Cost of Funds：资金的All-in成本，不只票面利率，还包括承诺费、管理费、期限和对冲等。

APR/CAT：定价必须看综合年化成本和现金流，不应只看名义利率；正式CAT以墨西哥适用监管方法为准。

ROI：渠道/产品应使用风险调整后ROI，纳入CAC、Funding Cost、EL和可变成本。

今日实操：Reject Sample / Challenger

目标：为历史拒绝边界客群获取真实标签，减少选择偏差。

字段：application_id、channel、score、rules、reject_reason、experiment_group、limit、term、disbursement、dpd1/3/7/30、bad、maturity、revenue、funding_cost、CAC、strategy_version。

步骤：定义边界区 → 排除明确欺诈/身份高风险 → 随机抽小比例低额度Challenger → 固定额度/期限 → 记录随机分流 → 等待成熟标签 → 比较风险与利润。

SELECT experiment_group,COUNT(*) n,AVG(approval_flag) approval,AVG(CASE WHEN maturity_flag=1 THEN fpd7_flag END) fpd7,AVG(contribution_margin) cm FROM reject_sample GROUP BY experiment_group;

复盘：第二天只看随机平衡、KYC、Disbursement、技术失败和FPD1；标签未成熟前不全量扩量。

今日业务：宏观变好为什么首贷利润仍可能下降？

GDP增长和总体通胀处于目标区间，不等于现金贷客群立即改善。核心服务通胀、低收入现金流、多头和资金成本仍可能压缩利润。复盘链路应是：宏观 → 收入/负债 → Approval/Take-up → EAD → FPD/Vintage → Funding Cost → Contribution Margin。

今日产品：拒绝用户的可恢复路径

把拒绝原因分为“不可恢复高风险”和“可补充/技术问题”。OCR失败、银行卡同名异常、资料不足等提供重试/二验；欺诈、身份高风险等不暴露具体阈值。用户侧原因保持稳定类别，内部保留细粒度Reason Code和Strategy Version。

职责：产品负责文案和申诉路径；风控维护Reason Taxonomy与可恢复标记；数据跟踪Reject→Retry→Approval→FPD→Complaint；研发支持版本与冷静期；运营不得绕过高风险拒绝。
