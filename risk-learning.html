今日知识｜AML Transaction Monitoring & Case Prioritization｜反洗钱交易监控与案件优先级

概念：AML Transaction Monitoring 的目标不是“让 Alert 越多越安全”，而是把 Customer/Geography/Product/Transaction/Device/Payer/Beneficiary 风险信号转成高质量 Alert，再通过 Triage 与 Investigation 决定 Close、持续监控、升级或法定报告。

Risk Assessment → Scenario/Model → Alert → Triage → Case → Investigation → SAR / STR / ROIU or Close → QA → Feedback

为什么重要：Alert 太少可能漏风险；Alert 太多且质量低，会制造 Backlog 和 Case Aging，让真正高风险Case延迟。监管关注的也不是单一规则，而是风险评估、控制、治理、记录和监控能否闭环。

墨西哥现金贷七步案例

背景：墨西哥数字现金贷 APP 对 SPEI 还款、第三方代还、异常账户变更和高频小额资金循环做 PLD/FT 监控；Rule Set V3 新增“第三方付款人 + 高频入账”。
数据：月监控交易120,000笔；Alert Rate 2.8%→5.1%；Alert-to-Case 42%→29%；Case-to-ROIU/STR 8%→6%；P90 Case Aging 36h→82h；Backlog 420→1,150。
现象：Alert接近翻倍，但真正升级Case和报告的Yield下降，调查队列明显变老。
拆解：噪声集中“老客×低金额×稳定设备×固定家庭成员代还”；高风险样本更集中“新设备×新付款人×多账户短周期资金循环×Bank Change”。
根因：可以确认 V3 导致低风险 Alert 激增和Case Aging恶化；但不能直接认定低金额第三方代还没有风险，仍需成熟Case Outcome与QA验证。
决策：稳定低风险第三方代还降级为监控/低优先级；新设备+新付款人+资金循环保持高优先级；Queue按Customer Risk、Amount、Network、Velocity、Rule Severity排序。
结果：连续2-4周观察 Alert Rate、Alert-to-Case、Case-to-Report、P90 Aging、Backlog、高风险Case SLA、QA Error，确保“降噪不漏高风险”。

指标/公式：Alert Rate = Alerts ÷ Monitored Transactions/Customers；Alert-to-Case = Escalated Cases ÷ Mature Alerts；Case-to-Report = Filed Reports ÷ Mature Closed Cases；Case Aging = Observation Time − Case Created Time。

判断方法：固定Rule/Model Version → 分母/去重 → Alert Yield → Case Aging/Backlog → Risk Segment → Outcome/QA → Rule Tuning / Priority / Staffing。

常见误区：Alert=可疑交易；报告率越高越好；把低价值Alert全部自动清除；只按金额排Case；Aging上升只靠加人；不同规则版本直接横比。

小练习与答案

120,000笔交易产生6,000 Alert，1,800升级Case，成熟Case中120提交法定可疑报告。三个比例分别是多少？

答案：Alert Rate=5.0%；Alert-to-Case=30.0%；Case-to-Report≈6.7%。若P90 Aging同时从36h升到80h，应优先检查低质量扩量与优先级，而不是只看Alert总量。

今日指标学习

AML Alert Rate：监控系统产生警报的密度，必须与 Rule Version、Alert-to-Case、Backlog 联看。

Alert-to-Case Escalation：初筛后真正升级调查的比例，帮助识别低质量规则与Triage噪声。

Case-to-SAR/STR/ROIU：成熟调查Case中最终形成法定可疑报告的比例，不同司法辖区标准不同，不能把“越高越好”当KPI。

AML Case Aging / TAT：案件从创建到处置的时效，建议至少报告P50/P90/P95，并分高风险/普通风险。

今日实操｜AML Queue Health × Rule Yield Matrix

字段：alert_id、customer_id、transaction_id、rule_id、rule_version、alert_time、case_id、case_created、case_closed、case_outcome、report_flag、customer_risk、country_risk、amount、channel、payer_account、beneficiary_account、device_id、velocity_features、analyst、qa_result。

步骤：统一Alert/Case去重 → 固定Rule Version → Alert Rate → Alert-to-Case → Case-to-Report → P50/P90 Aging → Backlog → Rule×Risk×Channel×Network拆分 → QA/Confirmed Pattern复盘。

Alert Rate ↑ + Alert-to-Case ↓ + Case-to-Report ↓ + P90 Aging ↑ = 低质量扩量 / Queue Health 恶化强信号

第二天复盘：抽样检查被降优先级或自动关闭的Case是否漏风险，并确认高风险Case Aging 是否下降；不要用“Alert减少”单独证明策略成功。

今日业务｜Fraud、KYC、AML 统一到同一客户风险图谱

固定链路：获客/注册 → KYC/Device → 申请/授信 → 放款账户 → 还款付款人 → Bank/Beneficiary Change → 复借 → 逾期/催收 → Fraud/AML Case。第三方还款、新设备、账户变更、多账户循环等信号应被Fraud与AML共同消费，避免团队信息孤岛。

今日产品｜高风险触发加强验证，低风险减少无差别摩擦

对 New Device + New Payer/Beneficiary + Bank Change + High-value Drawdown/Repayment Anomaly 触发更强Step-up；对稳定设备、成熟老客、固定低风险第三方代还可走轻验证或低优先级监控。产品负责页面与恢复路径，风控负责Trigger，数据负责Alert→Outcome，研发负责日志与幂等，运营/AML Analyst不得删除审计证据或绕过强规则。
