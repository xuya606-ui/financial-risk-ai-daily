风控指标学习卡｜支付风险专题

今日完整学习4个指标：Payment Failure Rate、Auto-debit Success Rate、Bank Account Match Rate、Repayment Success Rate。所有阈值与案例数字为训练用模拟数据，不代表行业统一标准。

1. Payment Failure Rate｜支付失败率

1）指标是什么：进入支付执行的尝试中，有多少没有成功。大白话：系统“发起扣款/还款”后，多少次没真正完成。

2）为什么重要：它同时反映支付技术、银行接口、账户状态和客户余额，是FPD1的重要上游同步指标。对现金贷特别重要，因为技术故障很容易被误判成信用恶化。

3）精确定义与公式：

Payment Failure Rate = 失败支付尝试数 ÷ 总有效支付尝试数

分母只包含真正发送给支付通道/银行的有效尝试；前端未提交、重复幂等请求、测试流量应排除。建议同时按“支付尝试”和“受影响订单/用户”两个口径报告。

4）如何看高低：通常越低越好，但失败率上升并不等于信用风险变差。必须先区分Provider Timeout、Bank Routing Error、Invalid Account、Insufficient Funds、User Cancel等原因。

5）墨西哥现金贷案例七步法（模拟）

背景：首贷14天产品在还款日前升级支付SDK。
数据：成熟订单18,000；Payment Failure 7%→19%；Auto-debit Success 83%→69%；FPD1 21%→30%；FPD3 17%→19%；FPD7 15%→15.8%。
现象：FPD1大幅恶化，但风险没有继续迁移到FPD7。
拆解：按Error Code拆分，新增失败主要来自Provider Timeout和Bank Routing Error；余额不足占比基本不变。
根因：技术/路由故障是更强候选原因；通过备用通道回放可进一步确认因果。
决策：恢复备用路由、增加智能重试，不收紧信用准入；技术失败单独标记。
结果：观察Failure、Retry Recovery、FPD1/3/7、投诉和Collection Load是否恢复。

6）诊断逻辑：①Error Code → ②Provider/Bank → ③App/SDK Version → ④Retry Recovery → ⑤FPD3/7与余额不足占比。

7）策略动作：技术型失败切备用路由/重试；Invalid Account触发账户重新验证；Insufficient Funds进入现金流风险和催收。

8）常见误区：所有失败都归因为余额不足；交易次数与用户数混用；Provider重试产生多次失败但只影响一个订单。

9）推荐拆分：Provider、Bank、Error Code、Payment Method、OS、App/SDK Version、新老客、渠道。

10）预警方式：技术指标用分钟/小时级历史基线；信用归因使用日级成熟FPD。黄/红灯阈值应根据自身Provider历史稳定区间设定。

11）指标关系：Payment Failure → Auto-debit/Repayment Success → FPD1 → FPD3/7 → Collection → Bad/EL。

12）小练习

Failure从6%升到18%，FPD1同步+9pp，但FPD7只+0.5pp，首先检查什么？

参考答案：Error Code、Provider/Bank和SDK版本，优先排技术故障。

2. Auto-debit Success Rate｜自动扣款成功率

1）指标是什么：到期自动扣款尝试中真正成功扣款的比例。

2）为什么重要：它直接影响FPD1、早期催收工作量和还款体验，属于贷后同步指标，并可作为支付通道稳定性的领先技术信号。

3）公式：

Auto-debit Success Rate = 成功自动扣款尝试 ÷ 有效自动扣款尝试

建议同时报告First-attempt Success、Retry Success和最终D+1成功率；Mandate无效、换卡、账户关闭等需单独归因。

4）如何看高低：高通常更好，但如果通过频繁重试产生客户投诉或重复扣款风险，也不能只追求数字。低成功率需要区分余额不足和技术/账户问题。

5）案例七步法

背景：自动扣款从Provider A切至Provider B。
数据：First Success 84%→70%；Retry Recovery 28%→61%；最终D+1还款成功80%→79%；投诉率基本稳定。
现象：第一次扣款明显变差，但通过重试大部分恢复。
拆解：失败集中在特定银行的路由窗口。
根因：首次路由时段与Bank响应更相关，非客群信用恶化。
决策：调整重试时点、保留备用Provider并做银行级路由。
结果：看First Success、Final D+1 Success、投诉和FPD3。

6）诊断：首次成功 → Error Code → Retry → Bank/Provider → Account Change → Insufficient Funds。

7）动作：智能重试、到期前提醒、备用路由、换卡后重新建立必要授权。

8）误区：只看第一次扣款；自动扣款成功率等同最终还款率；忽略重复扣款和用户体验。

9）拆分：Bank、Provider、Time Slot、新老客、Payment Mandate Age、App Version。

10）预警：First Success和Final Success双基线；若First下降但Final稳定，优先技术优化，不应直接升级信用预警。

11）关系：Mandate/Account → Auto-debit Success → FPD1 → Collection Load → Cure。

12）小练习

First Success从85%降到72%，但D+1最终成功仍80%，应该如何判断？

答案：首先是路由/重试效率问题，不宜直接解释为客户还款能力显著下降。

3. Bank Account Match Rate｜银行账户同名匹配率

1）指标是什么：用于放款或还款的银行卡/CLABE中，账户持有人与借款人身份一致的比例。

2）为什么重要：它连接KYC、收款账户欺诈、代申请、ATO和放款失败，是贷前/贷中领先指标。

3）公式：

Bank Account Match Rate = 通过持有人一致性校验的账户 ÷ 完成校验的有效账户

必须固定姓名标准化逻辑，包括双姓、重音符号、中间名、顺序、缩写和Vendor返回的匹配等级。

4）如何看高低：通常越高越好，但短期下降可能是Bank/Vendor数据格式变化，不一定是欺诈增加。

5）案例七步法

背景：接入新的账户持有人校验接口。
数据：Match 92%→84%；Disbursement Success 93%→88%；Fraud Rate 3.6%→3.7%；Mismatch集中双姓和重音字符。
现象：匹配率下降，但欺诈没有同步上升。
拆解：Bank×Vendor×姓名格式发现技术兼容问题。
根因：姓名标准化和Vendor规则变化是主要候选原因。
决策：改标准化、弱Mismatch进入二验；强冲突叠加高风险设备才拒绝。
结果：观察Match、Disbursement、Fraud、申诉和人工审核率。

6）诊断：Name Normalization → Vendor/Bank → KYC Name → Device/ATO → Mature Fraud。

7）动作：技术型Mismatch修映射；多个强身份冲突则增加Step-up或人工审核。

8）误区：所有不匹配都判欺诈；中文/西班牙语姓名标准化规则不统一；放款账户与还款账户场景混用。

9）拆分：Bank、Vendor、Name Pattern、Region、New/Repeat、Device Risk。

10）预警：Vendor变更后按小时/日监控；Match下降但Fraud稳定时先查技术。

11）关系：KYC Identity → Bank Match → Disbursement/Account Change → Fraud/ATO → Fraud Loss。

12）小练习

Match下降8pp但Fraud只升0.1pp，且刚更换Vendor，第一动作？

答案：按Vendor/Bank/姓名格式回溯，不应直接全量硬拒。

4. Repayment Success Rate｜还款成功率

1）指标是什么：到期或进入还款流程的订单中，最终成功完成还款的比例。

2）为什么重要：它综合反映支付体验、账户状态与客户支付能力，是贷后同步/结果指标。

3）公式：

Repayment Success Rate = 成功完成还款的有效订单 ÷ 到期/进入还款流程的有效订单

建议区分Full Repayment、Partial Repayment、Technical Pending；件数和金额口径均可报告。

4）如何看高低：高通常更好，但业务大幅收缩、展期增加也可能让表面Success改善；需要与DPD、Cure、Collection一起看。

5）案例七步法

背景：主动还款页面上线新流程。
数据：Repayment Success 74%→66%；Page Error 2%→9%；Payment Failure 8%→15%；DPD7 16%→17%；投诉上升35%。
现象：还款成功率下降明显，但深度逾期只轻微变化。
拆解：App Version×Payment Method显示新版本页面超时。
根因：产品/支付体验是更强候选原因。
决策：回滚页面、增加备用支付方式和失败一键重试。
结果：观察Success、Page Error、Payment Failure、DPD1/7和投诉。

6）诊断：Payment Entry → App/Provider → Error Code → Retry → Partial Payment → DPD/Cure。

7）动作：优化还款路径、备用通道、到账状态刷新、失败后保留账单与参考号。

8）误区：按支付尝试而非订单计算；部分还款视为完全成功；未区分技术Pending和真实失败。

9）拆分：Payment Method、Provider、Bank、App Version、DPD Bucket、New/Repeat。

10）预警：与Page Error、Payment Failure、FPD/DPD、投诉联动；技术指标用实时基线。

11）关系：Repayment UX → Payment Success → DPD/Cure → Collection → Recovery → LGD。

12）小练习

Success下降10pp、投诉翻倍，但DPD7只升1pp，首先怀疑什么？

答案：还款页面/支付技术异常，而不是直接判定信用客群大幅恶化。
