现金贷 APP 海外投放学习日报｜2026-08-29

过去24小时无重大平台硬规则新增；今日扩展到最近两周，重点关注 Android 归因反作弊与墨西哥 TikTok 金融广告政策纠偏。

1）今日最新资讯

AppsFlyer Protect360 Advanced Security：Android 归因反作弊升级

发生了什么：AppsFlyer 在 2026 年 8 月更新的 Protect360 Advanced Security 模块中，强化 Android App 对 SDK Spoofing、Attribution Spoofing 和被操纵流量的识别。该模块在首次 App Launch 之后、正式 Attribution 之前进行检测，可在归因写入前阻断可疑安装；官方特别提到该能力适合高流量 App、尤其是使用 Affiliate/第三方流量的客户。官方英文说明还要求 Android SDK 至少为 6.15.2。

为什么重要：现金贷很容易被“前端数据好看”误导：假安装、伪造 in-app event、设备农场或归因劫持都会让 CPI、CPA 看起来下降，但真实 Register、Apply、Disburse 和风险质量没有同步改善。越是按 Install/Apply 结算或使用联盟流量，越需要把 MMP 数据和自有后端真实行为交叉验证。

对投放的影响：以后不能只看媒体或 MMP 面板的 Install/Apply。建议至少同时看 App Store/Google Play 安装、自有 backend first_launch、Register、Apply、Disburse，并按 Publisher/Media Source/Geo/App Version 拆分。

建议动作：Android 高量账户今天先检查 SDK 版本、Protect360/Validation Rules 能力、MMP 与 backend 的安装/事件差异，并把异常 Publisher 单独进入观察或限量名单。

官方原文：AppsFlyer Advanced Security Protect360 ｜ AppsFlyer Validation Rules ｜ Protect360 Anti-fraud Guide

重要纠偏｜TikTok Mexico 金融广告政策以当前官方原文为准

重新核对 TikTok 当前 Financial Services Policy 的 Mexico 市场段落后，昨天知识库的两点判断需要纠正：

  1. 普通金融服务/贷款并没有统一要求 Sales Representative Permission。Mexico 所在市场组明确要求当地/区域许可、必要 disclosure/disclaimer、18+；Sales Representative application permission 在该段落中明确用于 cryptocurrency / crypto trading / NFT 等特定类别。
  2. Mexico 当前禁止清单确实包含 High APR Loan（APR ≥50%）、Payday Loan、Short-term Loan（还款周期 ≤90 天）。因此这三项仍应作为当前 TikTok Mexico 官方限制执行。

同一官方段落还把 mortgage、consumer finance、P2P 和 BNPL loans 列为 may be allowed 的示例，因此不能再把 P2P 一概写成 Mexico 禁止类别。

官方原文：TikTok Financial Services Policy（EN） ｜ TikTok Financial Services Policy（ES-LATAM）

【墨西哥重点】当前 TikTok 贷款广告执行口径

当地/区域许可 + 必要披露 + 18+ + 不属于禁止类别

可投示例：consumer finance、mortgage、P2P、BNPL 等在官方页面中属于 may be allowed 示例，但仍需满足当地法律、资质和具体审核要求。

明确禁止：High APR Loan（APR ≥50%）、Payday Loan、Short-term Loan（≤90天）、credit repair、FX、复杂投机产品等当前禁止清单项目。Crypto/NFT 类别另有 Sales Representative application permission 要求。

2）海外投放知识学习

SDK Spoofing、Install Hijacking、Device Farm、Post-attribution Fraud 有什么区别？

SDK Spoofing

攻击者伪造 App SDK 发给 MMP 的网络请求，让服务器以为发生了真实 Install 或 in-app event，但真实设备可能根本没有安装/运行 App。

Install Hijacking

真实用户确实安装了 App，但欺诈方伪造最后一次 engagement，把原本属于自然量或其他渠道的 Attribution 抢走。

Device Farm

大量真机/模拟器批量产生安装与事件。行为可能“看起来像真人”，但注册、KYC、授信、放款和还款质量通常异常。

Post-attribution Fraud

安装已经被归因后，MMP 通过后续统计/异常检测才确认欺诈。它不会让历史投放决策自动消失，因此财务结算和渠道复盘必须二次扣除。

现金贷判断原则：MMP 是“归因真相层”，backend 是“业务真相层”。两者必须对账；如果 MMP 有 Install/Apply，而 backend 没有 first_launch/user/application，就要高度警惕。

常见误区：① 只看 MMP Fraud Dashboard，不对账 backend；② Fraud Rate 低就认为没有问题；③ 把 Organic 当绝对干净基线；④ 只拦 Install Fraud，不看 In-app Event Fraud；⑤ 发现欺诈后只降媒体预算，不定位具体 Publisher、App Version、Geo、Device/OS。

官方/行业原文：AppsFlyer Protect360 Guide ｜ Adjust Anonymous IP Filtering
3）实操训练

30 分钟做一次 MMP × Backend 反作弊体检

  1. 取数：最近 7 天和 28 天，按 Media Source / Publisher / Campaign / Geo / App Version 拆出 MMP Install、MMP Register/Apply、backend first_launch、backend Register、backend Apply、Disburse。
  2. 做差异：计算 MMP-to-Backend Install Gap、Backend Verified Conversion Rate、Fraud Block Rate、Post-attribution Fraud Rate。
  3. 看时间：检查 Click→Install、Install→Register、Register→Apply 的异常尖峰。大量“秒级完成”或高度同质时间分布要重点调查。
  4. 看设备/网络：检查同设备/IP/ASN/数据中心聚集、模拟器、匿名 IP、异常新设备比例；高风险 Publisher 做单独 cohort。
  5. 看业务质量：将 Fraud/异常分组继续接到 Approve、Disburse、FPD7、Vintage。低 CPI 但 backend verification 与授信/放款明显差的渠道优先限量。

内部试验阈值（非 AppsFlyer/Adjust 官方标准）：若 MMP Install 比 backend first_launch 高出超过 5%，先预警；超过 10% 或某 Publisher 的差异率达到全账户均值 2 倍以上，进入专项排查。真实阈值应结合埋点丢失率、SDK版本、网络环境和历史基线校准。

次日复盘：不要只看“被拦多少”，而要看净有效首贷 CAC 是否改善，以及被拦 Publisher 的后端质量是否验证了欺诈判断。

4）业务分析

为什么 CPI、Apply CPA 都变好，首贷 CAC 和 FPD 却恶化？

假设某联盟渠道花费 100,000 MXN，MMP 显示 10,000 Install、2,000 Apply：

CPI = 10 MXN
Apply CPA = 50 MXN

看起来非常便宜。但 backend 只确认 7,500 个真实 first_launch、1,200 个真实 Apply，最终 300 个 Disburse：

真实首贷 CAC = 100,000 ÷ 300 = 333 MXN

如果其中风险质量又较差，FPD7 从 18% 升到 27%，那么“便宜流量”实际上同时污染了媒体效率和风险判断。更危险的是，如果平台继续用伪造/低质 Apply 学习，算法会反向寻找更多相似流量。

正确业务链：Spend → MMP Valid Install → Backend Verified Apply → Approve → Disburse → FPD/Vintage → Risk-adjusted LTV。现金贷扩量应该以“后端验证后的有效首贷”做分母，而不是未验证的前端事件。

5）产品相关

建立 Attribution Trust Layer：让投放事件必须经过“可信度”校验

产品经理
定义哪些事件可作为平台优化事件，哪些需要 backend confirmation；设计异常流量状态和运营处置流程。
投放
按 Media Source / Publisher 维护质量白名单、观察名单和限量规则；不能只按 MMP CPA 扩量。
数据
维护 MMP install_id/click_id → user_id → application_id → loan_id 映射，输出 Fraud、Gap、Verified Conversion、FPD/LTV。
风控
把设备/IP/账户关联、团伙、异常申请速度和 FPD/Vintage 与渠道/Publisher 联动，识别“营销欺诈 + 信贷欺诈”重叠。
研发
升级 SDK、服务端事件签名/幂等、event_id、时间戳、版本监控；关键 Apply/Disburse 事件优先采用 backend 真实状态回传。

建议新增内部对象：Attribution Trust Score，输入 MMP fraud flags、backend verification、device/network anomaly、publisher history、event timing consistency；输出 Trusted / Review / Blocked。这个分数仅用于内部治理，不直接把敏感信贷字段发送给广告平台。
