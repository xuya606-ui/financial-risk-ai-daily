现金贷 APP 海外投放学习日报｜2026-09-10

重点：TikTok Landing Page View（LPV）× Smart+ Traffic × Web-to-App 页面加载质量；把“点击便宜”升级成“页面真的打开、申请真的发生、首贷和风险真的健康”。

1）今日最新资讯

TikTok 9 月更新 LPV：Traffic Campaign 可以直接优化“点击后页面成功加载”

截至 2026-09-10，本轮官方核查没有发现过去 24 小时内会改变 Mexico 现金贷核心广告准入边界的 Meta / Google / TikTok 新禁投规则。当前最值得执行的是 TikTok 2026 年 9 月更新的 Landing Page View（LPV）：TikTok 将其定义为 Traffic Objective 下的优化目标，只有当用户点击广告且目标 Landing Page 成功加载时才计为一次 LPV。LPV 由 TikTok 在页面加载时计算，与广告主通过 Pixel / Events API 上报的 View Content、Default Page View 不是同一个事件。

TikTok 官方原文：Landing Page View — Last updated September 2026

为什么重要：现金贷 Web-to-App 经常出现“Click 很多，但页面没真正打开”的损失，原因可能来自移动网络、页面过重、重定向、第三方脚本、低端设备、浏览器兼容等。只优化 Click，算法可以找到更爱点的人，却不保证页面能加载；LPV 至少把媒体优化推进到“页面真实打开”这一层。

对投放的影响：TikTok 当前说明 LPV 适用于全球 Auction Ads，支持第三方 Landing Page 和 TikTok Instant Page，支持 TikTok / TikTok Ad Network、Lowest Cost / Cost Cap；默认 Traffic Campaign 仍是 Click，广告主需要主动切到 LPV。LPV 本身不要求先安装 Pixel，但仍可以在 Ad 层配置 Pixel Tracking。

TikTok 官方原文：LPV availability / setup / reporting

同时，TikTok 2026 年 9 月更新的 Smart+ Traffic Campaign继续明确：如果主要目标是 Click 或 LPV，可以使用 Smart+ Traffic；如果已经安装 Pixel / Events API，而且真正想推动更深的网站事件，则官方建议使用 Smart+ Web Campaign 去优化 Conversion，而不是永远停在 Traffic。

TikTok 官方原文：Smart+ Traffic Campaigns — Last updated September 2026

今天建议：把 Mexico Web-to-App 漏斗正式拆成 Impression → Click → LPV → Register/KYC → Apply → Approve → Disburse。如果 Click→LPV 损失高，先修页面与跳转；如果 LPV 健康但 Apply 低，再修产品承接；如果 Apply 健康但 Approve/FPD 差，再看流量质量与风控匹配。

【墨西哥重点】LPV 能改善“页面没打开”的问题，但不能替代金融广告准入与贷款披露

TikTok 当前 Mexico 金融服务广告仍要求遵守当地规则、取得所需当地/区域许可，并按平台要求完成许可/申请流程、面向 18+；禁止示例仍包括 APR≥50% 的 High APR Loan、Payday Loan、还款周期≤90天的 Short-term Loan。LPV 只是流量优化目标，不会让原本不可投的贷款产品变成可投。

TikTok 官方原文：TikTok Financial Services Policy — Mexico

Google Personal Loans 当前仍只允许需要 61 天或以上才能全部偿还的 personal loan，并要求 Landing Page 或 App 显著披露最短/最长期限、最高 APR 或当地等效年化口径，以及包含全部费用的代表性总成本。对 Mexico Web-to-App 来说，Landing Page 既是转化资产，也是合规资产。

Google 官方原文：Google Personal Loans

Mexico 产品判断：不要为了提高 LPV 而把页面“减重”到删掉必要贷款说明。正确目标是：加载更快 + 事实更清楚 + 披露仍完整 + 下一步 CTA 更明确。

2）海外投放知识学习

Click、LPV、Page View、Session、Conversion：五个最容易混淆的概念

Click 说明用户点了广告；LPV 进一步要求点击后页面成功加载；Default Page View / View Content 是广告主通过 Pixel / Events API 上报给 TikTok 的网站事件；Session 是 GA/分析工具按自身规则划分的一次访问会话；Conversion 则是你定义的 Register、Apply、Disburse 等目标行为。TikTok 官方明确提醒，LPV、Google Analytics Page View 和 Session 因定义与触发逻辑不同，出现差异是正常的。

TikTok 官方原文：LPV definitions and reporting differences
Landing Page Load Rate = LPV ÷ Ad Clicks
Click-to-LPV Loss Rate = 1 − LPV ÷ Ad Clicks
Cost per LPV = Spend ÷ LPV
LPV→Apply Rate = Backend Valid Applies ÷ Matched LPV
LPV→First-loan Rate = First Disbursed Borrowers ÷ Matched LPV

现金贷适用场景：Web-to-App、贷款预审页、H5 Landing Page、TikTok Instant Page、Search/Social 引导页。特别适合诊断“CTR 很好但注册/申请很差”究竟是页面没加载，还是页面加载后承接差。

常见误区：① 把 Click 当真实访问；② 用 LPV 代替 Apply/Disburse；③ TikTok LPV 与 GA Page View 不一致就判断埋点坏了；④ 页面为了提速删掉 APR/期限/费用等必要披露；⑤ 深层事件量已经足够，却仍长期优化 LPV，导致算法停留在浅层流量。

判断方法：先看 Click→LPV，再看 LPV→Apply，再看 Apply→Approve→Disburse，最后看 FPD/Vintage/LTV。每一层只解决一种问题。

3）实操训练

今天做 Mexico Web-to-App「Click → LPV → Apply」漏斗体检

  1. 拉 14 天基线：按 Campaign / Ad Group / Placement / Creative / OS / Landing Page 拉 Spend、Clicks、LPV；Backend 同时拉 Register、KYC、Valid Apply、Approve、Disburse。
  2. 新增 5 个指标：Cost per LPV、Landing Page Load Rate、Click-to-LPV Loss Rate、LPV→Apply Rate、LPV→First-loan Rate。
  3. 分 OS / Network：Mexico Android 重点拆 4G/5G/Wi-Fi、系统版本、浏览器/内嵌 WebView；如果有 TikTok Ad Network，再单独看 Placement/Publisher。
  4. 检查页面：首屏 HTML/关键资源大小、重定向次数、第三方 SDK、DNS/TLS、JS 阻塞、图片/视频、Deep Link fallback、404/超时、表单首屏可见性、披露模块是否在关键内容加载前后正常显示。
  5. 实验方式：TikTok 当前 LPV 文档明确写明 LPV 与平台 Split Test 尚不兼容，因此不要把“无法开 Split Test”误判为产品问题。可以先用 matched cells：相近人群/素材/预算的两个 Ad Group，Control 优化 Click，Treatment 优化 LPV，保持其他变量尽量一致，并连续观察足够样本。
  6. 次日复盘：D1 先看 Delivery、Clicks、LPV、Load Rate、Cost/LPV；Apply、Approve、首贷 CAC 按真实漏斗继续成熟，FPD/Vintage 不做过早结论。
TikTok 官方原文：LPV setup — Split Test currently not supported

内部排查起点（非平台官方阈值）：Click-to-LPV Loss Rate 相较同 OS / Landing Page 的 28 天基线恶化 ≥5 个百分点，进入 P1；若绝对 Loss Rate ≥20%，进入 P0 页面/跳转专项。阈值应按你们自己的历史分布校准。

4）业务分析

CPC 便宜 33%，真正到达页面的成本反而更贵

假设两组 Mexico TikTok Traffic Campaign 都花 100,000 MXN：

方案 A（优化 Click）：5,000 Clicks → CPC=20 MXN → LPV=3,000 → Load Rate=60% → Cost/LPV≈33.3 MXN
LPV→Apply=20% → 600 Apply → Approve=35% → 210 Approve → Disburse=70% → 147 首贷
First-loan CAC≈680 MXN

方案 B（优化 LPV）：3,750 Clicks → CPC≈26.7 MXN → LPV=3,375 → Load Rate=90% → Cost/LPV≈29.6 MXN
LPV→Apply=22% → 743 Apply → Approve=35% → 260 Approve → Disburse=70% → 182 首贷
First-loan CAC≈549 MXN

表面上方案 A 的 CPC 比方案 B 便宜约 25%，但大量点击没有形成成功页面访问；方案 B CPC 更贵，却因为页面到达率更高，最终首贷 CAC 更低。这个例子不是在证明“LPV 一定优于 Click”，而是在说明媒体浅层指标必须沿真实漏斗向下验证。

更重要的是：如果 LPV→Apply 很高、Approve 却突然下降，问题大概率不在页面速度，而在流量意图、预筛、产品条件或风控策略；如果首贷 CAC 很好但 FPD/Vintage 恶化，则仍不能扩量。

5）产品相关

Landing Page Performance Contract：把页面加载、披露和业务转化做成跨团队契约

产品经理
维护 Landing Page Version、首屏信息结构、贷款期限/费用/资格说明、CTA、Web-to-App 跳转和 disclosure_version；不能以提速为理由删除必要披露。
投放
按 Campaign / Ad Group / Creative / Placement 看 Click→LPV 与 Cost/LPV；根据深层事件量决定使用 Smart+ Traffic 还是 Smart+ Web/Conversion。
数据
打通 click_id / campaign_id / adgroup_id / lp_version / session_id / user_id / application_id / loan_id，并统一 LPV、GA Session、Backend Visit 的口径说明。
风控
按 Landing Page / Creative Cohort 看 Approve、Fraud、FPD、Vintage，避免“页面变快”同时放大不匹配用户。
研发
负责首屏性能、Redirect、Deep Link/Fallback、WebView、Pixel/Events API、event_id、错误码、页面版本与关键资源监控。

建议状态：Draft → Compliance Approved → Performance QA → Active → Degraded → Rollback / Superseded。

建议自动告警：页面版本发布后，如果 Landing Page Load Rate 明显下降、LPV→Apply 断崖式变化、Redirect Error/Timeout 上升，应能够按 lp_version 自动回滚或停止导流。
