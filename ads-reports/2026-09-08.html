2）海外投放知识学习

Target Gap：tCPA、Actual CPA、First-loan CAC 为什么经常不是一回事

今天把三个概念彻底分开：

tCPA = 你告诉平台希望优化到的“目标事件成本”
Actual CPA = 实际 Spend ÷ 平台/统一口径下的目标事件数
First-loan CAC = Acquisition Spend ÷ 首次实际放款用户数

如果优化事件是 Apply，那么 tCPA 本质上是“申请成本目标”，不是“首贷 CAC 目标”。现金贷应该把业务目标反推回平台 target：

Business-derived Apply tCPA ≈ Allowable First-loan CAC × Mature Apply→Disburse Rate

墨西哥案例：如果业务允许的 First-loan CAC 上限是 800 MXN，成熟 Apply→Disburse Rate=25%，那么理论上的 Apply tCPA 上限约为 200 MXN。如果 Google 账户还把 tCPA 填成 350–400 MXN，就算平台“达标”，真实首贷 CAC 也可能远超经营上限。

今天新增一个内部指标：Target Gap Ratio。

Target Gap Ratio = (Platform Target − Mature Actual CPA) ÷ Mature Actual CPA

Gap 很大而且为正，表示 target 相比近期成熟实际成本更宽松；在 Google 新行为下，这类 Campaign 最值得优先审计。

适用场景：Google Search/PMax/Demand Gen 的 Limited by budget Campaign、历史实际显著好于 target 的 Campaign、准备放大 Budget 的 Campaign。

常见误区：把 target 当 KPI 而不是算法约束；只按近 1–3 天 CPA 回调 target；不同 Campaign 的优化事件不同却直接比较 tCPA；用 Apply tCPA 代替 First-loan CAC；风险恶化时仍把旧的 Allowable CAC 当不变。

判断方法：先让 target 对齐成熟业务，再让平台去扩量。最终顺序应是：Target → Mature Actual CPA → Apply→Disburse → First-loan CAC → FPD/Vintage → Risk-adjusted LTV / Payback。

Google 官方原文：Target-based bidding changes ｜ Target ROAS / value-based bidding

今天执行：Mexico Google Bid Target Alignment Audit

  1. 筛 Campaign：导出 Mexico 的 Search / PMax / Demand Gen，筛出 Limited by budget + tCPA/tROAS/Target CPC；Google App Campaign 单独标记，不纳入本轮规则变化影响集。
  2. 固定 28 天成熟口径：记录 Target、Mature Actual CPA/ROAS、Spend、Optimization Event、Conversion Lag、Apply、Approve、Disburse、First-loan CAC、FPD7/Vintage。
  3. 算 Target Gap：优先检查 Target Gap Ratio 大、且历史实际明显优于 target 的 Campaign。
  4. 反推 Business-derived Target：若优化 Apply，使用 Allowable First-loan CAC × Mature Apply→Disburse Rate；若优化 Value，先定义可用于营销优化的合法 Conversion Value，不能把贷款本金直接当利润 Value。
  5. 只改一个核心变量：使用 Bid Target Adjustment Tool 或手动修改 target；为便于归因，实验期尽量不要同时大改 target、budget、landing page、optimization event。
  6. 等待成熟：至少观察 1–2 个 conversion cycles，再比较 Mature Actual CPA、First-loan CAC、FPD/Vintage，而不是第二天就判失败。

内部预警逻辑：可先用 Target Gap Ratio ≥ +30% 作为 Review 起点；若业务反推 target 与平台当前 target 偏差 ≥20%，进入 P0 审核。这是内部运营阈值，不是 Google 官方标准。

次日复盘：只先看 Delivery、Spend、Actual CPA 是否开始向新 target 收敛；First-loan CAC 和风险指标继续等成熟，不做过早结论。

4）业务分析

Google “达成 tCPA”，为什么首贷 CAC 反而能恶化 67%

假设 Mexico Search Campaign 优化事件为 Apply，Daily/周期 Spend 为 120,000 MXN。

旧阶段：Actual Apply CPA = 240 MXN → 500 Apply
成熟 Apply→Disburse = 30% → 150 首贷
First-loan CAC = 120,000 ÷ 150 = 800 MXN

但账户里长期填写的 tCPA 是 400 MXN。在 Google 新行为完全生效后，如果系统更接近这个 target：

新阶段：Actual Apply CPA ≈ 400 MXN → 300 Apply
若 Apply→Disburse 仍为 30% → 90 首贷
First-loan CAC = 120,000 ÷ 90 ≈ 1,333 MXN

结果是平台看起来“终于按 400 tCPA 正常交付”，但真实首贷 CAC 从 800 升到约 1,333 MXN，恶化约 67%。

更关键的是，如果为了拿更多便宜 Apply 而放宽流量后，Approve Rate / FPD 同时变差，风险调整后的 LTV/CAC 会进一步恶化。因此 target 必须由业务反推，而不是沿用几个月前随手填写的数字。

5）产品相关

建立 Bid Target Registry + Business Target Translator

产品经理
定义每个获客漏斗的业务目标事件、产品版本、Landing Page、KYC/Apply/Disburse 口径；维护 Allowable CAC 的业务版本。
投放
维护 campaign_id、bid_strategy、platform_target、budget_status、Limited-by-budget 状态、target change log；不能只写“CPA 目标”。
数据
每天计算 Mature Actual CPA、Target Gap Ratio、Apply→Disburse、First-loan CAC、conversion cycle；把 target 与业务结果放同一张表。
风控
按 Campaign/Cohort 提供 Approve、FPD、Vintage、Fraud，动态修正 Allowable CAC；风险恶化时同步收紧业务 target。
研发
保证 Google Ads / GA4 / MMP / Backend 的 event_id、conversion value、offline/S2S 回传和 schema_version 稳定，所有 target 变更可审计可回滚。

建议 Registry 字段：platform / campaign_id / campaign_type / optimization_event / bid_strategy / platform_target / mature_actual / business_derived_target / target_gap_ratio / budget_status / p50_conversion_lag / p90_conversion_lag / allowable_first_loan_cac / apply_to_disburse / fpd7 / ltv / effective_from / owner。
