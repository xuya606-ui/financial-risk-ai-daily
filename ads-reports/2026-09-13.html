现金贷 APP 海外投放学习日报｜2026-09-13

今日主线：Google 9 月 10 日 Measurement Suite 更新 → First-party Signal Strength → Deep-funnel Conversion → Incrementality；现金贷必须同时建立敏感金融数据边界。

1）今日最新资讯

Google 发布新一轮 Measurement Suite：Data Manager API 统一化、Data Strength Uplift、Meridian GeoX 全球可用

Google 于 2026-09-10公布一组测量产品更新。核心包括：将 Data Manager 更深入接入 Google Analytics / DV360；Data Manager API 走向通用化；在 Google Ads 中引入 Data Strength Uplift，用于估算 First-party Data Setup 带来的额外可恢复转化；同时宣布 Meridian GeoX 已全球 General Availability，可用 Geo Experiment 的因果增量结果校准 MMM。

Google 官方原文：Drive profitable growth with new data and measurement tools — 2026-09-10 ｜ Meridian GeoX

为什么重要：广告平台正在把“数据接得更多”与“是否真的创造新增业务”分成两层。前者解决 Signal Recovery / Measurement Completeness，后者通过 GeoX / MMM 回答 Incrementality。现金贷不能把“平台多识别了 Conversion”直接当成“新增了更多优质首贷”。

对投放的影响：未来自动出价越来越依赖 First-party Signal，但金融行业需要先定义哪些事件可以作为营销信号、哪些属于禁止或高风险数据。Google 的 Customer Data Policy 明确禁止将与敏感类别相关的 Conversion 用于 Enhanced Conversions，其中明确包括负面金融状况，例如低信用评分或高负债。

Google 官方原文：Customer data policies — Restrictions on measurement in sensitive categories ｜ Enhanced conversions introduction

建议动作：不要把 Credit Score、Debt Load、逾期、催收、Reject Reason、风险等级等用户级字段直接发送给广告平台。优先构建经过法务/隐私/平台政策评审的业务阶段事件，例如 Registered、KYC Completed、Valid Application、Disbursed（是否用于具体平台优化仍需逐项审核），并通过 Backend 聚合结果做风险质量判断。

【墨西哥重点】深层事件可以更接近业务，但不能越过金融数据边界

TikTok 当前 Mexico 金融广告政策仍要求广告主具备当地/区域所需许可并仅面向 18+；Loans 属于可能允许的金融产品类型。TikTok 的 Anti-Discrimination Policy 同时明确，广告主不能利用广告工具对信贷机会进行违法歧视，也不能基于个人金融困境等属性进行不当定向。

TikTok 官方原文：Financial Services Advertising Policy — Mexico ｜ Anti-Discrimination Ad Policy

Google Personal Loans 当前仍要求：贷款必须需要 61 天或以上才能完全偿还，并在 Landing Page/App 显著披露最短/最长期限、最高 APR（或当地法律一致的等效口径）以及包含全部费用的代表性总成本。

Google 官方原文：Google Personal loans policy

Mexico 业务今天建议把平台反馈信号分成两层：Marketing-safe Event Layer 用于测量/优化；Risk Truth Layer 只留在内部 Backend 做 Approve、FPD、Vintage、LTV 和 Fraud 判断。不要把两层混成一个“高质量用户标签”回传平台。

2）海外投放知识学习

Signal Recovery ≠ Incrementality：平台多识别的 Conversion 不等于新增业务

今天学习两个常被混淆的概念：

Signal Recovery：原来发生了但平台没识别，现在通过更好的 Tag / API / Matching 被识别出来。
Incrementality：如果没有这次广告，本来不会发生的新增业务。

Data Strength Uplift 更接近第一类：衡量 First-party Data Setup 让平台恢复了多少额外 Conversion Visibility。GeoX / Holdout / Lift 才是第二类：通过控制组与实验组估计 Counterfactual，回答真实增量。

现金贷例子：Spend 不变，Google 从 800 个 Apply 识别到 1,000 个 Apply，可能只是 Enhanced Conversion / Data Manager 提高了匹配覆盖；只有在 Holdout/Geo Experiment 中，Treatment 的真实首贷、风险调整利润或 LTV 相对 Counterfactual 明显上升，才能说产生了 Incremental Value。

常见误区：把平台 Attribution Conversion 当 Incremental Conversion；把 Match Rate 提升当用户质量改善；把 Disbursement 金额直接当 Value；为了“更深层优化”把信用分、逾期、拒绝原因等敏感金融信息回传平台。

官方：Google Data Strength / Meridian Updates ｜ Meridian GeoX methodology
3）实操训练

今天做一次 Mexico Deep-funnel Signal Boundary Audit

  1. 拉出当前 Google / TikTok / MMP 所有正在接收的事件与参数：event_name / event_source / user_data / custom_parameters / value / currency / timestamp / event_id。
  2. 把事件分为三类：A 可用于营销测量候选（如 Register/KYC/Valid Apply）；B 仅内部经营（Approve/Disburse 的内部明细与利润计算）；C 敏感/禁止外传（Credit Score、Debt Load、Delinquency、Collections、Reject Reason、Risk Grade、Black/White List 等）。具体平台是否允许 A/B 事件仍需按平台政策与当地法律逐项审核。
  3. 建立 Event Data Contract：每个事件必须写明业务定义、触发时点、来源系统、允许参数、禁止参数、Consent/Privacy Basis、平台用途、Owner、schema_version。
  4. 对 Google 检查 Enhanced Conversions / Data Manager 是否存在敏感金融状态字段；对 TikTok Events API 检查是否有风险标签、逾期/催收或信用分字段进入 payload。
  5. 建立双层看板：Signal Health 看 Event Coverage、Match/Recovery、Dedup；Business Truth 看首贷 CAC、Approve、FPD/Vintage、Risk-adjusted LTV。

内部判断起点：Sensitive Parameter Leakage = 0；Event Contract Coverage = 100%；关键事件 Dedup Coverage ≥99%；任何新的 Deep-funnel Event 上线前必须完成 Product + Data + Risk + Privacy/Compliance Review。以上为内部治理建议，不是平台官方阈值。

次日复盘：先确认事件是否完整、重复、延迟和越界，再观察 CPA；不要因为平台 Conversion 突然上涨就立即放量。

4）业务分析

平台多恢复 25% Conversion，首贷 CAC 和风险收益可能完全没变

假设 Mexico Google Campaign：

Spend = 120,000 MXN
原平台识别 Apply = 800 → Platform Apply CPA = 150 MXN
Data Strength 改善后识别 Apply = 1,000 → Reported Apply CPA = 120 MXN

表面上 CPA 改善了 20%。但 Backend 实际仍然是：

Valid Apply = 1,050
Approve = 315
Disburse = 220
First-loan CAC = 120,000 ÷ 220 ≈ 545 MXN
FPD7 = 20%

如果投放前后 Backend 的 220 个首贷和 FPD7 都没有变化，则这次改善主要是测量覆盖提升，不是业务增长。真正的经营问题仍是：新增预算是否能带来新增首贷，而且这些首贷的 FPD/Vintage/LTV 是否健康。

Signal Recovery → Better Bidding Signal → Incremental Test → Mature First-loan CAC → FPD/Vintage → Risk-adjusted LTV → Payback / ROI

对现金贷而言，Incrementality 最终最好落到风险调整后的新增价值，而不是 Install、Apply，甚至不是未扣风险成本的 Disbursement。

5）产品相关

建立 Event Signal Registry + Sensitive Data Firewall + Incrementality Ledger

产品经理
定义 Register/KYC/Apply/Approve/Disburse 的产品语义、触发点和版本；避免营销事件名承载信用结论。
投放
明确每个平台 Optimization Event、Attribution Window、使用目的；禁止自行新增风险字段。
数据
维护 Event Contract、Event ID、Dedup、Latency、Data Strength/Match、Backend 对账与 Geo Experiment 数据集。
风控
信用分、债务负担、拒绝原因、逾期、催收、风险等级留在内部 Risk Truth Layer；输出聚合经营结论。
研发
在 S2S / Events API / Data Manager Pipeline 前增加字段 Allowlist、Schema Validation、PII/Sensitive Scanner、Kill Switch。
event_name / business_definition / source / platform_destination / allowed_params / blocked_params / consent_basis / schema_version / owner / effective_from / sunset_at

Incrementality Ledger 额外记录：experiment_id、channel、geo/cell、treatment、control、incremental_first_loans、incremental_risk_adjusted_value、confidence_interval、decision。这样平台“报告变好”和业务“真实新增”会被系统性区分。

今日结论

平台更“看得见”你的转化，是 Measurement Improvement；广告真正创造了原本不会发生的优质首贷，才是 Incrementality。现金贷下一阶段的数据能力不是“回传越深越好”，而是“回传足够有效、合法合规、最小必要的营销信号，同时把信用风险真相留在内部”。
