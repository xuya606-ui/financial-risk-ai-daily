2）海外投放知识学习

AdAttributionKit / SKAN：为什么 iOS 广告“数据变少”不等于业务变差

AdAttributionKit 是 Apple 的隐私保护广告归因框架；它基于 SKAdNetwork 的能力，让广告网络和广告主在不依赖跨 App 个体追踪的前提下获得安装、再互动和转化信号。Apple 会基于 crowd anonymity / privacy threshold 决定 Postback 能包含多细的数据，因此 Fine Conversion Value 缺失或只返回 Coarse Value，并不自动代表埋点失败。

Apple 官方原文：AdAttributionKit ｜ Ad Attribution overview

核心链路：广告触达 → iOS 安装/再互动 → App 更新 Conversion Value → Apple 依据隐私层级生成 Postback → 广告网络/开发者接收并验证。Apple 支持 Fine Conversion Value，也支持 `low / medium / high` 的 Coarse Conversion Value；开发者还可以通过 lockPostback/lockWindow 更早锁定信号，但会牺牲后续继续更新 Conversion Value 的空间。

现金贷例子：可以把早期且非敏感的漏斗阶段映射成 Conversion Value，例如 First Launch → Register → KYC Complete → Submit Application；只有在真实发生时间落入可用窗口、并经过合规/隐私审查时，才考虑更深事件。不要把收入、信用评分、审批额度、逾期标签等用户级敏感金融字段编码成营销归因值。

常见误区：把 SKAN/AdAttributionKit 当成 MMP 的替代品；把 Fine Value 缺失当成 Fraud；用平台 Postback 直接计算 FPD/Vintage；或者为了拿更快 Postback 过早 lock window，导致深层事件永远无法写入。

判断方法：iOS 投放至少同时看三个层：Apple Postback 的可用性与验证 → MMP/平台的聚合归因 → Backend 的真实 Apply/Approve/Disburse/FPD。业务真相最终仍在 Backend。

3）实操训练

今天做一次 iOS Postback × Backend 对账

  1. 拉数据：取最近 28 天 iOS Campaign，准备 Apple/MMP Postback、Install、Register、Apply、Approve、Disburse、Spend、Campaign/Ad Group/Creative 和 App Version。
  2. 先验签：只统计 Apple 签名验证通过、`postback-identifier` 去重后的有效 Postback；无效签名不进入正式归因。
  3. 拆信号：分别统计 Fine Conversion Value、Coarse Conversion Value、无细粒度值的 Postback，占比不要混在一个“有效率”里。
  4. 对 Backend：同 Cohort 比较 Valid Postback → MMP Install → Backend First Launch → Apply → Disburse，不要求用户级强行一一对应，而是先看 Campaign/Day/Cohort 级趋势。
  5. 次日复盘：如果 Fine Value Availability 下降，但 Backend Install/Apply/Disburse 稳定，优先判断 privacy tier / volume mix；如果 Postback Verification Pass Rate 和 Backend 同时下降，再排查 SDK、endpoint、版本和网络。
Apple 官方原文：Verifying a postback ｜ Receiving attributions & postbacks

内部预警起点：可以先对每个稳定 Campaign 建 28 天自身基线；Fine Value Availability 或 Verified Postback Rate 较自身基线下降超过 10pct 时触发排查。10pct 只是内部监控起点，不是 Apple 官方阈值。

4）业务分析

为什么 iOS “可见转化率”下降，首贷 CAC 可能完全没变？

假设 Mexico iOS Campaign 花费 100,000 MXN。上周有 4,000 个有效 Apple Postback，其中 3,000 个带 Fine Conversion Value；本周仍有 4,000 个有效 Postback，但只有 2,200 个带 Fine Value。如果只用 Fine Value 统计 Apply proxy，会得到“可见转化下降 26.7%”的结论。

但 Backend 同期首贷都是 200 人：

Backend First-loan CAC = 100,000 ÷ 200 = 500 MXN

业务 CAC 实际没有变化。差异可能来自隐私数据层级、流量规模/分布或 Postback 细粒度变化，而不是用户真的变差。

因此 iOS 的经营顺序应该是：Postback Data Quality → MMP Aggregate Attribution → Backend First-loan CAC → FPD/Vintage → LTV。如果只按“带 Fine Value 的人数”做预算，很容易把隐私噪声误判成业务变化。

5）产品相关

建立 iOS Attribution Contract：把 Conversion Value 当“聚合信号协议”管理

产品经理
定义可用于归因的漏斗事件、价值层级和 `conversion_schema_version`；禁止把敏感金融属性直接编码。
投放
维护 Campaign / MMP / Apple schema 对应关系，解释 Fine/Coarse signal 与优化事件差异。
数据
建设 Postback 验签、去重、Data Tier、Fine/Coarse availability、Backend Cohort 对账。
风控
FPD/Vintage/信用风险只在内部数仓按 Cohort 分析，不把用户级风险字段回传广告生态。
研发
维护 AdAttributionKit/SKAN 调用、AttributionCopyEndpoint、JWS 验证、`postback-identifier` 去重、lockPostback 策略与版本监控。

建议 Schema：`schema_version / conversion_type / fine_value / coarse_value / business_stage / effective_from / lock_policy / owner / privacy_review_status`。任何 Conversion Value 调整都要版本化，否则平台 ROAS/CPA 变化可能只是“编码规则变了”。
