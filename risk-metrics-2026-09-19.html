2026-09-19B. 贷前/征信

征信覆盖与 Thin-file｜4张完整指标学习卡

今日主题：Bureau Query Success Rate、Bureau Hit Rate、Thin-file Rate、Inquiry Velocity。所有阈值均应使用内部历史基线；模拟案例用于训练分析逻辑，不代表行业统一标准。

统一墨西哥现金贷案例

背景：30天首贷产品扩大年轻用户与自由职业者Channel C，同时切换部分征信查询链路。
数据：月申请60,000；Bureau Query Success 98%→94%；Bureau Hit 82%→69%；Thin-file 18%→31%；30日Inquiry中位数1.4→2.6；Alternative-data Coverage 76%→91%；Approval 30%→34%；FPD7 14.5%→18.2%；Avg Ticket 1,500→1,850 MXN。
现象：审批和额度上升，但征信覆盖下降、Inquiry上升、FPD7恶化。
拆解：Channel C×Thin-file×Limit≥2,000 的FPD7约25%；稳定工资、Inquiry低的Thin-file约13%；Technical Fail样本在重试成功后风险并未明显更差。
根因：可以确认客群结构、Inquiry和Limit变化与FPD恶化高度相关；不能把Thin-file直接写成唯一因果，也不能把技术失败当成信用风险。
决策：Technical Fail走Retry/Fallback；真实Thin-file用已验证的收入/设备/账户/历史付款信号分层；High Inquiry×High Limit先降额；稳定低Inquiry Thin-file保留Challenger。
结果：观察两个成熟FPD7 Cohort，并继续看MOB1 DPD30+、Amount FPD、EL/Loan、Approval、投诉、Contribution Margin。

1. Bureau Query Success Rate｜征信查询技术成功率

1）指标是什么：提交给征信机构的查询请求中，有多少成功返回了“可判定的技术响应”。大白话：先确认系统有没有真正查成功。

2）为什么重要：这是贷前同步/领先的技术质量指标。它解决“无征信结果到底是客户没档案，还是接口失败”的问题，位于Bureau Hit、评分和审批之前。

3）精确定义与公式：Query Success Rate = 技术成功且返回可判定状态的唯一查询 ÷ Eligible且已发起的唯一征信查询固定Vendor、接口版本、授权状态、超时窗口；重复Retry按Application/Decision Window去重。技术成功不代表一定有信用档案。

4）如何看高低：一般越高越好；突然下降常见于Vendor故障、授权错误、网络超时、字段格式、证件匹配问题。高成功率也不代表征信质量高。

5）七步案例：背景为Channel C扩量+查询链路切换；Query Success 98%→94%，Bureau Hit 82%→69%，FPD7 14.5%→18.2%；拆解发现新版SDK在部分Android版本超时显著；重试成功后的客户FPD并未显著更高；因此根因包含技术问题和客群变化；决策是Fallback/Retry与风险决策分离；结果看Query Success恢复、重复查询成本、Approval和成熟FPD。

6）诊断逻辑：①授权/Consent是否有效；②Vendor HTTP/Business Error；③OS/App/Network；④证件字段格式；⑤重试后Hit/Outcome。关联指标必须看Bureau Hit、Timeout、Latency、Retry Success、Approval。

7）策略动作：技术失败优先Retry/Fallback，不直接信用拒绝；持续Vendor故障切换备用供应商；授权缺失引导重新授权；大面积字段错误立即回滚版本。

8）常见误区：技术失败算No-hit；重复Retry每次都进分母；成功返回“无档案”算失败；不同Vendor SLA直接横比。

9）推荐拆分维度：Vendor、App Version、OS、Device、Network、Region、Channel、Document Type、Error Code、Strategy Version。

10）预警方式：用小时/日历史基线和最低查询量；例如“低于自身历史P10且Timeout同步升高”可设内部黄灯。具体95%/98%等数值只能是内部阈值，不是行业标准。

11）与其他指标关系：Consent/Data → Query Success → Bureau Hit → Score/Thin-file → Approval/Limit → FPD/Vintage。

12）小练习

10,000笔Eligible查询，9,500笔得到可判定技术响应。Query Success=95%。如果其中2,375返回无档案，仍然不能把它们算技术失败。

2. Bureau Hit Rate｜征信命中率

1）指标是什么：在技术查询成功的申请里，有多少能找到可用的信用档案。大白话：系统查成功之后，用户到底有没有可用征信历史。

2）为什么重要：贷前同步指标，决定信用评分、Inquiry、多头、历史还款等信息是否可用；对Thin-file、新客与渠道结构非常敏感。

3）精确定义与公式：Bureau Hit Rate = 返回有效可用信用档案的唯一申请 ÷ 技术查询成功的唯一申请分母必须排除Technical Fail。可用档案标准要固定，例如至少返回身份匹配且文件状态可解释。

4）如何看高低：高通常意味着正式信用体系覆盖更充分；下降可能是年轻/新到信用户占比上升、渠道变化、身份匹配问题或Vendor数据覆盖变化。低Hit不等于低风险或高风险。

5）七步案例：Query Success 94%，Hit 82%→69%，Thin-file 18%→31%，Approval 30%→34%，FPD7 14.5%→18.2%；Channel C命中最低，但其稳定工资+低Inquiry组表现尚可；高Limit组恶化明显；因此决定按File Depth/Inquiry分层而非No-hit统一拒绝。

6）诊断逻辑：①先固定Query Success；②看身份匹配/档案状态；③Channel/年龄/就业结构；④File Depth；⑤FPD/EL验证。

7）策略动作：Hit下降但Outcome稳定时不应自动收紧；真实No-hit进入Thin-file策略；身份匹配异常修KYC/字段；某渠道Hit下降且FPD恶化时降量/降额。

8）常见误区：用全部申请作分母；No-hit=好客；No-hit=坏客；不同征信机构Hit直接比较而不控制客群。

9）推荐拆分维度：Channel、Campaign、Age Band、Employment、Region、Vendor、Document Type、新老客、Strategy。

10）预警方式：按Channel/客群建立自身稳定区间；Hit下降只有在File Depth、Inquiry、FPD/EL同步恶化时才升级风险告警。

11）与其他指标关系：Query Success → Bureau Hit → Thin-file/File Depth → Score/Inquiry → Approval → FPD/EL。

12）小练习

9,500笔查询技术成功，7,125笔有有效档案，Bureau Hit=75%。不能用7,125÷10,000=71.25%作为标准Hit，因为把500笔技术失败混进了分母。

3. Thin-file Rate｜薄征信占比

1）指标是什么：有征信档案但信用历史深度不足的客户占比。大白话：不是“查不到”，而是“查得到但信息太少”。

2）为什么重要：贷前同步/领先指标。它决定模型可用特征、准入不确定性和替代数据需求；对于年轻用户、新到信与正式金融渗透不足客群尤其重要。

3）精确定义与公式：Thin-file Rate = 符合内部Thin-file定义的Bureau-hit唯一申请 ÷ Bureau-hit唯一申请Thin-file定义必须版本化，例如 Tradeline Count、Oldest Tradeline Months、Active Credit Count 等组合。不存在行业唯一公式。

4）如何看高低：占比上升不一定坏，可能意味着业务成功触达新到信人群；但如果同时高Inquiry、高Limit和FPD上升，风险可能被低估。

5）七步案例：Thin-file 18%→31%，Channel C×Thin-file×Limit≥2,000的FPD7 25%，而稳定工资+低Inquiry Thin-file约13%；因此现象不是所有Thin-file都坏；根因更可能是Segment Mix+Limit；决策为分层Challenger与Limit Guardrail；结果看FPD7、MOB1、EL和Margin。

6）诊断逻辑：①Thin-file规则版本；②File Depth分布；③Inquiry/Income/Device；④Limit/Term；⑤成熟FPD/Vintage。

7）策略动作：稳定低Inquiry Thin-file可用小额度验证；高Inquiry/高波动收入降额或加强验证；替代数据必须经过稳定性/偏差/隐私验证；不要因Thin-file自动拒绝。

8）常见误区：No-hit=Thin-file；不同Thin-file定义混用；替代数据覆盖多就认为风险可控；只看件数风险不看EAD。

9）推荐拆分维度：Channel、Age、Employment、Income Type、Inquiry、Limit、Term、Device、新老客、Region。

10）预警方式：按同策略版本和客群建立Thin-file占比；当Thin-file上升且High Inquiry、Amount FPD、EL同步恶化可设内部黄灯。

11）与其他指标关系：Bureau Hit → Thin-file → Alternative-data/Income/Device → Limit → FPD/Vintage → EL/LTV。

12）小练习

7,000个Bureau-hit客户中2,100个符合Thin-file定义，Thin-file Rate=30%。若其中低Inquiry稳定工资用户FPD明显低于高Inquiry组，应分层而非统一收紧。

4. Inquiry Velocity｜征信查询速度 / 多头申请速度

1）指标是什么：客户在固定时间窗内被金融机构查询信用报告的次数或新增查询速度。大白话：最近是不是突然到处申请借款。

2）为什么重要：贷前领先指标，可捕捉多头借贷、资金压力和申请攻击；但查询可能包含比价、银行例行查询或不同业务，因此必须区分查询类型。

3）精确定义与公式：Inquiry_7d / Inquiry_30d = 决策时点前7/30天内符合内部“信贷申请查询”定义的唯一查询数必要时按Institution/Inquiry Type去重；时间必须只使用决策时点之前，避免数据穿越。

4）如何看高低：一般快速上升意味着资金需求/多头压力增加，但并非所有查询都等价。对成熟优质客户、按揭/汽车集中比价等需要产品化解释。

5）七步案例：30日Inquiry中位数1.4→2.6；High Inquiry×Thin-file×High Limit FPD7约25%；Low Inquiry稳定工资Thin-file约13%；相关性明显但Channel与Limit同时变化；决策为高Inquiry降额/收准入，低Inquiry保留；观察两个成熟Cohort确认因果。

6）诊断逻辑：①Inquiry Type/去重；②7d/30d增量；③Bureau Depth；④Channel/Score/Limit；⑤FPD/Amount FPD/EL。

7）策略动作：短周期爆发查询可降额、延迟或Step-up；稳定客户的合理查询不应机械拒绝；明显重复/异常查询先查Vendor或身份盗用。

8）常见误区：把所有查询都当借贷申请；使用决策后查询造成穿越；只看30天总量不看7天速度；因果倒置——坏账后产生更多催收/查询被误当贷前原因。

9）推荐拆分维度：7d/30d Window、Inquiry Type、Institution Type、Channel、Score、Thin-file、Limit、Region、Device、New/Repeat。

10）预警方式：使用自身历史分位数和最小样本量；例如High Inquiry占比连续两个批次升高且FPD/EL同步上升为内部黄灯。具体“3次/5次”等阈值不是行业统一标准。

11）与其他指标关系：Income Stress / Acquisition → Inquiry Velocity → Multi-Borrowing → Limit/EAD → FPD/Roll → Bad/EL。

12）小练习

客户过去30天有6次查询，其中过去7天有5次；另一个客户30天6次但分散在整月。即使30天总量相同，前者的短期Velocity更高，应单独评估。

指标组合建议

Query Success ↓ + Hit稳定 + Outcome稳定 → 技术问题优先Hit ↓ + Thin-file ↑ + Inquiry ↑ + FPD/EL ↑ → 客群/信用风险黄灯Thin-file ↑ + Low Inquiry + Stable Income + FPD稳定 → 可保留Challenger，不宜机械拒绝
