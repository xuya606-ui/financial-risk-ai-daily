【墨西哥重点】先统计真实 P50/P90 Lag，再决定 Apply / Disburse 的窗口

建议从墨西哥成熟 Cohort 统计 Click/Install → Register → Apply → Approve → Disburse 的延迟分布。若 Apply 的 P90 只有 3 天、Disburse 的 P90 是 11 天，两者就不该使用同一个回溯窗口。

内部起始框架（非平台官方阈值）：Register 1–3 天、Apply 3–7 天、Disburse 根据实际 P90 测试 7–14 天或更长；最终要同时看跨渠道重叠、自然转化和成熟首贷 CAC。

归因设置不会改变贷款广告准入。Google 个人贷款政策仍要求至少 61 天才能全额还清，并显著披露最短/最长期限、最高 APR/当地等效年化口径和代表性总成本。

官方原文：Google Ads：Préstamos personales

今日知识

Attribution Window ≠ Conversion Lag ≠ Attribution Model

Attribution Window 决定“多久以内还有资格归因”；Conversion Lag 是用户真实转化延迟；Attribution Model 决定多个触点都在窗口内时信用如何分配。

真实行为产生 Lag → Window 决定是否可归因 → Model 决定归给谁/怎么分

今天新增 CTC、EVC、VTC、Lookback Window 等术语。

官方原文：Google Ads：Conversion lag reporting ｜ Google Ads：Conversion windows

今日实操

做一张“转化延迟分布表”

用 60–90 天成熟 Cohort，计算 Register / Apply / Approve / Disburse 相对广告触达的 P50/P80/P90 Lag；再用 Google Ads 的 Days to Conversion 与 Conversion Lag reporting 交叉验证。只选 1–2 个稳定 Campaign 做窗口实验，不要全账户一次性从 7 天改到 30 天。

官方原文：Google Ads：Find conversion lag data

业务分析

7 天 CPA 250 MXN，14 天变成 200 MXN，不代表业务提升 20%

100,000 MXN 花费在 7 天内归因 400 笔放款，CPA=250；到 14 天累计 500 笔，CPA=200。差异可能只是延迟转化回补。若新增 100 笔里存在自然回访、Push/WhatsApp 召回或其他媒体触点，长窗口还可能过度归因。

最终决策：成熟首贷 CAC + FPD/Vintage + 风险调整 LTV，而不是“窗口调长后的平台 CPA”。

产品协同

建立 Attribution Control Center

统一管理 event_name、Google/Meta/TikTok window、MMP window、内部数仓规则、P50/P90 Lag、Provisional/Mature 状态、版本和负责人。最近数据默认标“未成熟”，同时展示 Provisional CPA 与 Mature CPA，防止日内数字驱动频繁调预算。
