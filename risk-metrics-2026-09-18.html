2026-09-18｜AML 交易监控完整指标学习卡

今日四项：AML Alert Rate、Alert-to-Case Escalation Rate、Case-to-SAR/STR/ROIU Conversion Rate、AML Case Aging / Investigation TAT。数值阈值仅为内部示例，不能冒充行业统一标准；SAR/STR/ROIU 等报告名称与法定义务按司法辖区执行。

1. AML Alert Rate｜反洗钱警报率

1）指标是什么：交易监控规则/模型在被监控交易、账户或客户中产生 Alert 的密度。大白话：系统每天“叫警报”的频率有多高。

2）为什么重要：属于同步/领先运营指标，主要用于发现规则阈值、流量、客户结构和交易行为变化。它解决的是“监控系统有多敏感”，不是“洗钱风险有多高”。适用于交易监控与贷后/支付阶段。

3）精确定义与公式：Transaction-level Alert Rate = 唯一Alert数 ÷ 被监控交易数Customer Alert Rate = 产生至少1个Alert的唯一客户数 ÷ 被监控客户数必须固定 Rule/Model Version、时间窗口、去重逻辑、是否一笔交易可产生多个Rule Hit；件数和金额不应混用。成熟期对 Alert Rate 本身要求较低，但后续Yield需等 Case Outcome 成熟。

4）如何看高低：升高可能意味着真实风险增加，也可能是规则变严、Vendor字段变化、季节性交易或重复Alert；降低可能意味着风险下降，也可能是数据丢失、规则失效。因此不存在“越低越好”。

5）墨西哥现金贷七步案例

背景：墨西哥30天现金贷，Rule Set V3 新增“第三方付款人+高频入账”场景，覆盖 SPEI 还款和账户变更。
数据：月监控交易120,000笔；Alert Rate 2.8%→5.1%；Alert-to-Case 42%→29%；Case-to-ROIU/STR 8%→6%；P90 Case Aging 36h→82h；Backlog 420→1,150。
现象：Alert 数量接近翻倍，但后续升级率和报告Yield下降，队列明显变老。
拆解：噪声集中“老客×低金额×稳定设备×固定家庭成员代还”；高风险样本更多在“新设备×新付款人×多账户短周期资金循环×Bank Change”。
根因：可确认 V3 导致低风险 Alert 激增；但不能直接认定第三方代还无风险，需用成熟Case Outcome与QA验证。
决策：固定第三方低风险代还降优先级；新设备+新付款人+资金循环保持高优先级；对Rule做Champion/Challenger。
结果：观察2-4周 Alert Rate、Yield、P90 Aging、Backlog、高风险Case SLA、QA Error；若噪声下降且高风险覆盖不降，调整才有效。

6）诊断逻辑：先看 Rule/Model Version 与数据完整性 → 再看 Channel/Customer Risk/Rule Family → 再看 Alert-to-Case 与 Report Yield → 最后看 Backlog/Aging 和高风险覆盖。

7）策略动作：数据缺失先修数据；单Rule噪声高则调阈值/合并重复Alert；高风险渠道Alert上升且Yield也升则提高优先级；低风险Alert暴增则改为监控/批处理而非直接增加人工。

8）常见误区：至少包括：把Rule Hit直接当唯一Alert；不同版本直接比较；Alert高就认定洗钱增多；Alert低就认定风险下降；不拆客户级与交易级口径。

9）推荐拆分维度：Rule/Scenario、Customer Risk、Channel、Product、Region、Payer/Beneficiary Type、Device、Amount Band、Velocity、New/Repeat Customer、Rule Version。

10）预警方式：用自身稳定历史、同Rule Version和最小样本量。示例内部黄灯：Alert Rate超历史P90，同时 Alert-to-Case / Case-to-Report 下降且Backlog上升。该数值思路不是行业统一阈值。

11）与其他指标关系：Risk Signal → Alert Rate → Alert-to-Case → Case-to-Report → Investigation Cost / Regulatory Risk

12）小练习

120,000笔监控交易产生6,000个Alert，Alert Rate是多少？

答案：5.0%。若同时Alert-to-Case从40%降到25%，不能简单说“风险更高”，更可能需要先检查噪声和规则版本。

2. Alert-to-Case Escalation Rate｜警报升级案件率

1）指标是什么：经过初筛后的 Alert 中，真正升级为正式 AML Investigation Case 的比例。大白话：系统叫了100次，最终有多少值得人工认真查。

2）为什么重要：同步运营与质量指标，解决“Alert是否有调查价值”和“人工产能是否被噪声占用”。适用于监控→调查阶段。

3）精确定义与公式：Alert-to-Case = 升级为正式Case的成熟唯一Alert ÷ 已完成Triage的成熟唯一Alert必须固定Triage窗口、去重规则、一个Case合并多个Alert时的归属方式；不能用尚未完成Triage的Alert作为分母。

4）如何看高低：过低常意味着规则噪声高或Triage过严；过高也不一定好，可能是Alert入口已经过度过滤、漏掉弱信号。应与Report Yield、Case Quality、Missed Risk联看。

5）墨西哥案例

背景：同一Rule Set V3上线。
数据：Alert 6,120；完成Triage 5,900；升级Case 1,711；Alert-to-Case≈29%；旧版本约42%；P90 Case Age 82h。
现象：大量Alert在初筛阶段被关闭，但仍消耗审核资源。
拆解：Rule A第三方低额代还Escalation仅12%；Rule B新设备+新付款人+Bank Change为68%。
根因：Rule A边际调查价值偏低；Rule B对真正高风险模式更集中，但仍需Case Outcome验证。
决策：Rule A降为低优先级批量Triage；Rule B设置Fast Lane；合并同客户短时间重复Alert。
结果：观察Backlog、P90 Age、Case-to-Report和QA，不因Escalation率上升就自动认为策略更好。

6）诊断逻辑：Triage成熟度 → Alert去重 → Rule/Scenario → Customer Risk → Case Outcome → Report Yield / QA。

7）策略动作：低Escalation高量Rule优先调阈值；高Escalation高风险Rule进入Fast Lane；高Escalation但后续Report Yield低则检查Analyst标准与Case定义。

8）常见误区：未完成Triage的Alert进分母；一个Case合并多个Alert重复计算；把高Escalation直接等同高风险；忽略不同Rule Family差异。

9）推荐拆分维度：Rule、Customer Risk、Channel、Amount、Velocity、Payer/Beneficiary、Device、Analyst Team、New/Repeat Customer。

10）预警方式：同Rule Version历史带。示例：高量Rule的Escalation持续低于自身P10且Backlog上升，可进入噪声治理黄灯；不是行业阈值。

11）与其他指标关系：Alert Volume × Escalation → Case Volume → Case Aging / Backlog → Report Yield / QA

12）小练习

5,900个完成Triage的Alert中1,711个升级Case，Escalation约多少？

答案：29.0%。

3. Case-to-SAR / STR / ROIU Conversion Rate｜案件转法定可疑报告率

1）指标是什么：成熟AML调查Case中，最终因达到法定/内部报告条件而提交可疑报告的比例。不同司法辖区可能称 SAR、STR、ROIU 等。

2）为什么重要：属于滞后质量/产出指标，连接规则、调查与法定义务，帮助判断Case Queue的“有效产出”，但绝不是越高越好。

3）精确定义与公式：Case-to-Report = 最终提交法定可疑报告的成熟Case ÷ 已完成调查并可形成最终处置的成熟Case必须排除Open Case、未成熟Case，并区分客户级报告、事件级报告和多Case合并一份报告的映射。

4）如何看高低：过低可能是Alert/Case质量差；过高可能是Case入口过窄，只留下极端风险。不同国家法定报告标准不同，绝不能横向用一个统一比例评价团队。

5）墨西哥案例

背景：Rule V3后Case量增加。
数据：成熟关闭Case 1,600；最终报告96；Case-to-Report=6%；旧版本8%；P90 Age 82h；高风险新设备组合报告率21%。
现象：总Case更多，但报告率下降。
拆解：低风险第三方代还Case报告率1.5%；新设备+新付款人+资金循环21%；高额跨账户快速循环28%。
根因：Case Mix被低风险场景稀释，不足以证明整体AML风险下降。
决策：低Yield场景调Rule/Triage；高Yield场景Fast Lane并补图谱；加强QA确认没有因压力导致少报。
结果：观察Report质量、补件/退回、QA、监管反馈、高风险覆盖与Missed Case，而非追求固定报告率。

6）诊断逻辑：Case成熟度 → Jurisdiction/Reporting Standard → Rule/Segment Yield → QA → Missed/Retrospective Finding。

7）策略动作：低Yield规则优化；高Yield高风险加优先级；报告下降且QA/追溯发现漏报则提升培训与二次复核；避免为了“提高比例”压缩Case入口。

8）常见误区：Open Case进分母；不同国家报告标准横比；把报告率当KPI越高越好；多个Case合并一份报告后重复计数。

9）推荐拆分维度：Rule、Risk Rating、Channel、Customer Type、Region/Country、Amount、Network Pattern、Analyst Team、Case Outcome。

10）预警方式：与历史成熟Case和QA结合。示例：报告率下降同时Retrospective Miss上升，才是强红灯候选；单独下降不一定坏。

11）与其他指标关系：Alert Quality → Case Yield → Report Yield → Regulatory Reporting Quality → Financial Crime Risk

12）小练习

1,800个成熟关闭Case中120个提交报告，Case-to-Report是多少？

答案：6.7%。

4. AML Case Aging / Investigation TAT｜案件账龄与调查时效

1）指标是什么：从Alert/Case创建到完成调查、作出处置或提交报告所经历的时间。大白话：风险案件在队列里“躺了多久”。

2）为什么重要：同步运营与控制有效性指标。高风险Case处理过慢可能带来持续交易、漏报、监管和声誉风险；适用于AML Investigation阶段。

3）精确定义与公式：Case Age = Observation Time − Case Created TimeInvestigation TAT = Final Disposition Time − Case Created Time应至少报告P50/P90/P95，不只看均值；Open Case与Closed Case分开；法定期限与内部SLA分开。

4）如何看高低：通常越短越好，但过短也可能意味着调查质量不足或批量机械关闭。必须与QA、Report Yield、高风险Case覆盖联看。

5）墨西哥案例

背景：Rule V3使Alert量上涨。
数据：P50 Case Age 18h→31h；P90 36h→82h；Backlog 420→1,150；高风险Case中超过内部48h SLA比例9%→27%；QA Error 3%→5%。
现象：队列拥堵不仅影响低风险Case，也开始挤压高风险Case。
拆解：夜间班次、新Rule A、低金额第三方代还占用大量Analyst时间；高风险Rule B Case被排队。
根因：Alert低质量扩量 + Priority设计不足共同造成Aging恶化，不能只归因“人手不足”。
决策：高风险Case Fast Lane；低风险规则批量Triage；重复Alert合并；必要时临时增员但同步Rule Tuning。
结果：观察P90、高风险SLA breach、QA、Report Yield、Backlog；若只靠增员降低Aging但噪声仍在，不能视为根治。

6）诊断逻辑：Timestamp/数据完整性 → Backlog → Severity/Priority → Rule Mix → Analyst Capacity → QA/Outcome。

7）策略动作：高风险队列加权；低风险自动化但保留抽样QA；SLA持续超时且高风险Missed上升时升级P0；若只是数据延迟先修日志。

8）常见误区：只看平均TAT；Open Case被忽略；不同Severity混合；追求速度导致调查质量下降。

9）推荐拆分维度：Severity、Rule、Customer Risk、Analyst Team、Shift、Channel、Country/Region、Amount、Case Outcome。

10）预警方式：使用内部SLA和历史P50/P90。示例：高风险Case超过内部SLA比例连续升高且QA Error同步变差，可设红灯；具体小时数不是行业统一标准。

11）与其他指标关系：Alert Volume → Case Volume → Backlog → Case Aging → Delayed Action / Reporting Risk → Operational & Regulatory Risk

12）小练习

Case A 10h、B 12h、C 14h、D 20h、E 90h。只看平均时长30h是否足够？

答案：不够。必须看P50/P90或尾部，因为90h长尾可能代表最危险的队列拥堵。

四指标组合判断

Alert Rate ↑ + Alert-to-Case ↓ + Case-to-Report ↓ + P90 Aging ↑ = 低质量扩量 / Queue Health 恶化的强信号

但如果 Alert Rate ↑、Alert-to-Case ↑、Case-to-Report ↑ 且高风险Case Aging仍稳定，则可能是真实风险上升。最终仍需结合 QA、确认模式、监管标准与业务结构判断。
