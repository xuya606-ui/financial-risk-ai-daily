今日完整指标学习卡

主题：欺诈闭环运营。今日新增/升级 Fraud Alert Rate、Alert-to-Case Conversion Rate、Time to Detect（TTD）、Time to Contain（TTC）。所有数字为模拟训练案例，预警阈值必须使用内部稳定历史，不冒充行业统一标准。

1. Fraud Alert Rate｜欺诈告警率

1）指标是什么

中文：欺诈告警率；英文：Fraud Alert Rate。大白话：有多少本来可以正常经过的申请/登录/交易，被系统打出了欺诈告警。

2）为什么重要

它解决的是“风险系统产生了多少需要处理的信号”，属于领先/同步运营指标，适用于贷前、贷中和支付/账户安全阶段。它影响审核量、用户摩擦和Fraud Ops成本，但不能直接代表欺诈捕获价值。

3）精确定义与公式

Fraud Alert Rate = 触发至少1个欺诈告警的Eligible事件数 ÷ Eligible风险事件总数

必须固定Eligible事件：申请、登录、换卡、提款、支付不能混成一个分母；还要区分Alert次数、Unique Event、Unique User。重复规则命中建议单独报Alert Density。

4）如何看高低

升高可能表示攻击增加、流量变差、规则放宽、数据异常或重复告警增加；下降可能表示风险改善，也可能是模型/规则失效。不是越低越好，也不是越高越安全。

5）墨西哥现金贷案例七步法

背景：首贷+复借APP新增Device Graph规则。
数据：月Eligible 80,000；Alert Rate 7%→13%；Unique Alert Users 5,100→8,300；Confirmed Fraud 980→1,180；FPR估算34%→48%；审核成本MXN0.42m→0.76m；Net Fraud Loss仅下降3%。
现象：告警几乎翻倍，但确认欺诈只小幅增长。
拆解：Rule×Channel×Device×CLABE×New/Repeat，发现大量告警来自同设备多个规则重复命中。
根因：重复/低增量信号与告警膨胀高度相关；是否完全导致FPR上升，还需控制渠道结构变化。
决策：同实体告警聚合，保留高Bad Capture组合；单一弱信号降级Step-up。
观察结果：观察2-4周的Unique Alert、Alert-to-Case、Confirmed Fraud、Net Fraud Loss和Review Cost。

6）诊断逻辑

① 分母/事件口径 → ② 重复告警/规则重叠 → ③ Channel/Device流量结构 → ④ Confirmed Fraud/FPR → ⑤ Fraud Loss。

7）策略动作

高Alert低价值：合并规则、降级二验、减少重复信号；高Alert高损失：加强限额/硬拒/实时封控；Alert突降：先排查数据/模型服务是否失效。

8）常见误区

把Alert次数当Unique用户；告警率高就认为模型更好；未成熟Case直接判FPR；申请和交易告警共用一个分母。

9）推荐拆分维度

Channel、Campaign、Signal Source、Rule/Model Version、Device、CLABE、Score、Limit、新老客、Scene。

10）预警方式

按同场景、同策略版本建立最近8周基线；建议联合黄/红灯：Alert Rate偏离 + FPR/Case Backlog/Net Fraud Loss同向恶化。具体百分比仅使用内部阈值。

11）与其他指标关系

Risk Signal → Fraud Alert Rate → Alert-to-Case → TTD/TTC → Confirmed Fraud → Net Fraud Loss → Contribution Margin。

12）小练习

Alert Rate从5%升到10%，Confirmed Fraud比例不变但Review Cost翻倍，应首先排查什么？

答案：重复告警、规则重叠和低增量Signal，而不是直接继续加规则。

2. Alert-to-Case Conversion Rate｜告警转案件率

1）指标是什么

大白话：系统打出的告警里，有多少真正值得进入人工/自动调查案件。

2）为什么重要

它衡量告警质量与Case容量之间的匹配，属于同步运营指标。过低可能说明信号噪声大；过高也可能是“什么都开Case”，导致运营成本过高。

3）精确定义与公式

Alert-to-Case Conversion = 由成熟Alert创建的Unique Case数 ÷ Eligible Unique Alerts

需要固定自动关闭、去重合并、批量团伙Case是否计为Case，并区分“进入调查”与“确认欺诈”。

4）如何看高低

升高可能是告警更精准，也可能是Case规则放宽；下降可能是Alert噪声增加，也可能是审核容量不足导致积压。

5）案例七步法

背景：墨西哥复借ATO策略上线。
数据：Alerts 6,000；Case 2,400→1,500；Conversion 40%→25%；Confirmed Fraud/Case 22%→28%；Case Backlog 300→1,100；Median TTD 18min→21min；TTC 55min→140min。
现象：Case转化下降，但进入Case后的确认率反而提高，同时积压和TTC恶化。
拆解：按Signal发现大量中风险Alert未及时进入Case，主要是审核容量不足。
根因：下降并非一定代表告警质量变差，Case容量是更强解释。
决策：高风险自动开Case+自动Contain；低风险聚合；中风险按金额/EAD优先级排队。
结果：观察Backlog、SLA、TTC、Fraud Loss和投诉。

6）诊断逻辑

① Alert去重 → ② Case创建规则 → ③ 审核容量/Backlog → ④ Confirmed Fraud per Case → ⑤ TTC/损失。

7）策略动作

低Conversion+高FPR：降噪；低Conversion+高Backlog：增容/自动化/优先级；高Conversion+低Confirmed Fraud：Case门槛太低。

8）常见误区

Conversion越高越好；把自动关闭Alert从分母剔除造成美化；一个团伙Case包含多人时重复计算。

9）推荐拆分维度

Signal、Fraud Type、Channel、Risk Band、Limit、Case Team、Strategy Version。

10）预警方式

同时监控Conversion、Backlog、Confirmed Fraud/Case、SLA；样本少时用周滚动而非日波动。

11）关系

Alert Rate → Alert-to-Case → Case Outcome → TTD/TTC → Fraud Loss / FPR。

12）小练习

Conversion下降，但Confirmed Fraud/Case上升且Backlog激增。一定是Alert变差吗？

答案：不一定，优先检查Case处理容量和优先级。

3. Time to Detect｜TTD｜风险发现时长

1）指标是什么

从第一个可识别风险事件发生，到系统生成有效欺诈告警的时间。大白话：坏事发生后，我们多久才发现。

2）为什么重要

属于领先/同步运营指标。尤其在ATO、支付欺诈、团伙申请中，检测慢几分钟就可能多发生多笔提款或多个账号损失。

3）公式

TTD = Alert Time − First Detectable Risk Event Time

建议报告Median、P90/P95；必须定义“First Detectable Event”，例如密码重置、新设备登录、共享CLABE出现，而不是用Case确认时间。

4）如何看高低

通常越低越好，但极速检测如果靠大量低质量Alert实现，会带来高FPR和用户摩擦。

5）案例七步法

背景：复借ATO，旧系统只在提款后做交易风控。
数据：新设备→换CLABE平均12分钟；换CLABE→提款8分钟；旧TTD Median 26分钟；新事件流上线后TTD 6分钟；ATO Fraud Loss MXN1.4m→0.9m；Step-up Rate 4%→7%；Abandon +0.6pp。
现象：TTD显著下降且损失下降，但用户摩擦略升。
拆解：Device Change×Password Reset×Bank Change×Limit；高额提款组收益最大。
根因：更早事件信号与损失下降高度相关，但仍需Challenger排除同期攻击强度变化。
决策：高风险组合在提款前Step-up/Contain；低风险新设备不硬拒。
结果：看TTD P90、ATO Loss、FPR、Abandon、Complaint。

6）诊断逻辑

① Event Time准确性 → ② 数据采集/流延迟 → ③ 模型计算延迟 → ④ Alert分发 → ⑤ 高损失Scene。

7）策略动作

TTD高：前移信号、实时流处理、缓存关键图谱；TTD低但FPR高：优化风险组合与门槛。

8）常见误区

用Case确认时间代替Alert时间；不同Fraud Type直接比较；只看Median不看P90；忽略客户端/SDK上报延迟。

9）拆分维度

Fraud Type、Signal Source、Scene、Device、Channel、App Version、Provider。

10）预警方式

实时场景建议监控P50/P90/P99并与Net Loss联动；阈值来自稳定期与业务可容忍损失窗口。

11）关系

First Risk Event → TTD → Alert → TTC → Prevented Loss → Net Fraud Loss。

12）小练习

TTD从20分钟降到5分钟，但FPR翻倍，是否一定成功？

答案：不一定，需要比较Prevented Loss、FPR、Review Cost和用户摩擦的净价值。

4. Time to Contain｜TTC｜风险控制时长

1）指标是什么

从有效告警/确认开始，到阻止进一步损失的控制动作真正生效所需时间。大白话：发现以后，多久真正把风险按住。

2）为什么重要

贷中/贷后同步指标。检测快但Contain慢，仍可能让攻击者继续提款、换卡或扩散到其他账号。

3）精确定义与公式

TTC = Containment Effective Time − Alert Time（或Confirmed Time，必须固定一种口径）

Containment可包括冻结提款、撤销Session、强制Step-up、Block Bank Account、团伙设备封控等。建议同时记录Contain Success Rate。

4）如何看高低

通常越低越好，但错误封控太快会提高申诉和好客损失。TTC必须和FPR、Complaint及Prevented Loss一起看。

5）案例七步法

背景：高风险ATO告警仍需人工审核后手动冻结提款。
数据：TTC P50 74min；P90 210min；告警后追加损失占总ATO Loss 38%；自动Contain Challenger使P50降至9min、P90 24min；追加损失下降62%；误封投诉0.3%→0.5%。
现象：自动化显著降低追加损失，但误封略升。
拆解：Risk Band×Limit×Account Change；极高风险组收益最大，中风险组误封较多。
根因：人工排队是TTC长的主要运营原因；自动化边界需要更精细。
决策：极高风险自动Contain，中风险Step-up+人工，高价值老客保留人工确认。
结果：看TTC P90、Post-alert Loss、Complaint、Override和Recovery。

6）诊断逻辑

① Alert→Case延迟 → ② Case Queue → ③ 人工审批 → ④ 工具/API执行延迟 → ⑤ Contain是否真正成功。

7）策略动作

高风险Scene自动Contain；中风险Step-up；增加Tool SLA、异步重试、备用封控接口；失败Contain自动升级。

8）常见误区

把“点击冻结”时间当“冻结生效”；只看平均值；忽略误封与投诉；不同起点口径混用。

9）推荐拆分维度

Fraud Type、Risk Band、Contain Action、Case Team、Limit、Tool/API、Strategy Version。

10）预警方式

重点看P90/P95、Contain Failure和Post-alert Loss；连续超内部SLA且损失同步升高时P0。

11）关系

Alert → Case → TTC → Prevented/Post-alert Loss → Recovery → Net Fraud Loss → Margin。

12）小练习

TTD只有5分钟，但TTC是3小时，攻击者在告警后继续产生40%的损失。优化重点在哪？

答案：优先优化Containment自动化、Case优先级和执行工具，而不是继续追求更低TTD。

今日指标组合

检测质量：Alert Rate + Alert-to-Case + Confirmed Fraud / Case + FPR。

速度：TTD P50/P90 + TTC P50/P90。

经营：Gross Fraud Loss − Recovery = Net Fraud Loss；再加Review Cost与Good Customer Friction进入Contribution Margin。
